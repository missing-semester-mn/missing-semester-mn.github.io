Сайн код бичихэд "анхааралтай бай" гэдэг ганцаараа хангалтгүй. Форматлагч, линтер,
тест, CI зэрэг хэрэгслүүд өдөр тутмын жижиг алдааг эрт барьж, багийн кодыг нэг
хэв маягтай байлгахад тусалдаг. Энэ лекцээр дараах зүйлсийг үзнэ:

- [Кодыг форматлах](#formatting)
- [Линтер](#linting)
- [Тест](#testing)
- [Pre-commit hook](#pre-commit-hooks)
- [Тасралтгүй интеграц (CI)](#continuous-integration)
- [Команд ажиллуулагч](#command-runners)

Нэмээд [regular expression буюу regex](#regular-expressions)-ийг үзнэ. Regex
кодын чанарын хэрэгслүүдэд (жишээ нь нэрээр нь шүүж тест ажиллуулах), мөн IDE-ийн
хайх/солих гэх мэт өдөр тутмын ажилд их хэрэглэгддэг.

Эдгээр хэрэгслийн ихэнх нь хэл бүрд өөр нэртэй байдаг. Python дээр
[Ruff](https://docs.astral.sh/ruff/) линтер/formatter ашиглаж болно, зарим
хэрэгсэл олон хэл дэмждэг ([Prettier](https://prettier.io/) гэх мэт). Гэхдээ суурь
санаа нь бараг бүх хэл дээр адил: форматлагч, линтер, тестийн сан заавал олдоно.

# Кодыг форматлах {#formatting}

Автомат форматлагч кодын хэлбэрийг автоматаар цэгцэлдэг. Ингэснээр хашилт `'` юу
`"` юу, `x+y` юу `x + y` юу, `import`-ууд ямар дарааллаар байх вэ гэх жижиг
маргаанд цаг үрэхгүй. Форматлагчийн хамгийн том давуу тал нь багийн бүх хүний код
нэг хэв маягтай харагддагт байгаа.

Prettier зэрэг зарим хэрэгсэл [их нарийн тохируулагддаг](https://prettier.io/docs/configuration);
тэр тохиргооны файлаа төслийнхөө [хувилбарын хяналт](/2026/version-control/)-д
оруулах хэрэгтэй. Харин [Black](https://github.com/psf/black),
[gofmt](https://pkg.go.dev/cmd/gofmt) зэрэг нь өчүүхэн зүйлийн төлөөх маргааныг
([bikeshedding](https://en.wikipedia.org/wiki/Law_of_triviality)) багасгахын тулд
тохиргоог зориуд цөөн байлгадаг эсвэл огт өгдөггүй.

Форматлагчаа [IDE-тэйгээ холбож](/2026/development-environment/#code-intelligence-and-language-servers)
тохируулбал бичиж байх зуур эсвэл файл хадгалах бүрд код автоматаар форматлагдана.
Мөн төсөлдөө [EditorConfig](https://editorconfig.org/) файл нэмээд файлын төрөл
бүрийн догол мөрийн хэмжээ гэх мэт төслийн түвшний тохиргоог IDE-дээ хэлж өгч болно.

# Линтер {#linting}

Линтер кодыг ажиллуулалгүйгээр статик шинжилгээ хийж, муу хэв маяг (antipattern)
болон гарч болзошгүй алдааг олдог. Эдгээр нь форматлагчаас илүү гүнзгий, гаднах
хэлбэрээс цааш шалгадаг. Хэр гүнзгий шинжлэх нь хэрэгслээс хамаарна.

Линтерүүд төслийн түвшинд тохируулж болох *дүрмүүд* болон бэлэн дүрмийн багцуудтай
ирдэг. Зарим дүрэм алдаагүй кодыг алдаатай гэж андуурах (false positive) тохиолдол
гардаг тул файл эсвэл мөр бүрээр нь унтрааж болно.

Сайн линтер дүрэм бүрийнхээ тайлбар, баримт бичигтэй байдаг --- дүрэм яг юуг шалгаж
байгаа, яагаад муу вэ, илүү сайн хувилбар нь юу вэ гэдгийг заадаг. Жишээ нь Python-ы
кодонд шаардлагагүй давхарласан `if`-ийг илрүүлдэг [Ruff](https://docs.astral.sh/ruff/)-ийн
[SIM102](https://docs.astral.sh/ruff/rules/collapsible-if/) дүрмийн баримт бичгийг
үзээрэй.

Зарим линтер зөвхөн анхааруулаад зогсохгүй, тодорхой асуудлуудыг автоматаар засаж
чаддаг.

Хэлний линтерээс гадна [semgrep](https://github.com/semgrep/semgrep) гэдэг
"утгаар хайдаг grep" хэрэг болж магадгүй. Энэ нь (grep шиг) тэмдэгтийн түвшинд биш,
AST (Abstract Syntax Tree) түвшинд ажилладаг бөгөөд олон хэл дэмждэг. Semgrep-ээр
төсөлдөө зориулсан тусгай линтерийн дүрэм амархан бичиж болно. Жишээ нь Python-ы
аюултай `subprocess.Popen(..., shell=True)` дуудлагыг хориглохыг хүсвэл тэр хэв
загварыг ингэж олно:

```bash
semgrep -l python -e "subprocess.Popen(..., shell=True, ...)"
```

# Тест {#testing}

Програм хангамжийн тест бол бичсэн код тань зөв ажиллаж байгаа гэдэгт итгэлтэй
болох стандарт арга. Код бичээд, дараа нь тэр кодыг ажиллуулж шалгадаг өөр код
бичнэ; код хүлээснээр ажиллахгүй бол тест алдаа заана.

Тестийг янз бүрийн түвшинд бичиж болно: тусдаа функцийг шалгах _unit тест_,
модуль эсвэл үйлчилгээнүүдийн хоорондын харилцааг шалгах _integration тест_,
хэрэглэгчийн хувилбарыг эхнээс нь дуустал шалгах _функциональ тест_. Кодоо
бичихээсээ өмнө тестээ бичдэг _тестэд суурилсан хөгжүүлэлт_ (test-driven development,
TDD) ч хийж болно. Кодноосоо алдаа олбол ирээдүйд тэр боломж дахин эвдрэхийг барих
_регрессийн тест_ бичиж болно. Мөн Haskell-ийн [QuickCheck](https://hackage.haskell.org/package/QuickCheck)-ээс
эхтэй, Python-ы [Hypothesis](https://hypothesis.readthedocs.io/) гэх мэт олон санд
хэрэгжсэн _шинж чанарт суурилсан тест_ (property-based test) бичиж болно. Аль арга
тохирох нь төслөөс тань хамаарна; магадгүй хэдийг нь хослуулах байх.

Програм тань өгөгдлийн сан, вэб API гэх мэт гадны хамааралтай бол тестийн үед
тэдэнтэй шууд харилцахын оронд хуурамч орлуулагч (_mock_) хэрэглэх нь
тохиромжтой байж болно.

## Кодын хамрах хүрээ (code coverage)

Code coverage бол тестүүд тань хэр сайн болохыг хэмжих үзүүлэлт. Тест ажиллах үед
кодын аль мөрүүд ажилласныг хянаж, кодын бүх хэсгийг шалгасан эсэхийг харуулна.
Coverage хэрэгслүүд мөр бүрээр тайлан гаргаж, дараа нь юунд тест бичихээ шийдэхэд
тусалдаг. [Codecov](https://app.codecov.io) гэх мэт үйлчилгээ төслийн түүхийн
туршид хамрах хүрээг хянах, харах вэб интерфейс өгдөг.

Бусад хэмжүүрийн адил coverage төгс биш; зөвхөн хувийг нь өсгөх гэж хөөцөлдөхийн
оронд чанартай тест бичихэд анхаараарай.

# Pre-commit hook {#pre-commit-hooks}

Git-ийн pre-commit [hook](https://git-scm.com/book/en/v2/Customizing-Git-Git-Hooks)-ыг
[pre-commit](https://pre-commit.com/) фреймворк ашиглахад амар болгосон. Hook нь
коммит хийх бүрд таны заасан кодыг автоматаар ажиллуулдаг. Төслүүд коммит бүрийн өмнө
форматлагч, линтер, заримдаа тестийг автоматаар ажиллуулж, код нэг хэв маягтай,
тодорхой алдаагүй байгааг баталгаажуулахад pre-commit hook-ыг өргөн хэрэглэдэг.

# Тасралтгүй интеграц (CI) {#continuous-integration}

[GitHub Actions](https://github.com/features/actions) гэх мэт тасралтгүй
интеграцийн (continuous integration, CI) үйлчилгээ таныг код push хийх бүрд (эсвэл
pull request бүр дээр, эсвэл тогтсон хуваарийн дагуу) скриптүүдийг тань ажиллуулж
өгдөг. Хөгжүүлэгчид CI-г ихэвчлэн форматлагч, линтер, тест зэрэг кодын чанарын
хэрэгслүүдийг ажиллуулахад хэрэглэдэг. Хөрвүүлэгддэг хэлд код хөрвөж байгааг,
статик төрөлтэй хэлд төрөл зөв байгааг шалгаж болно. Шинэ коммит бүрийг push хийх бүрд CI
ажиллуулбал кодын үндсэн хувилбарт орж буй алдааг барина; pull request дээр
ажиллуулбал оролцогчдын илгээсэн өөрчлөлтийн асуудлыг барина; хуваарийн дагуу
ажиллуулбал гадны хамаарлын асуудлыг барина (жишээ нь хөгжүүлэгч эвдэх өөрчлөлтийг
санамсаргүй [semver-тэй нийцтэй](/2026/shipping-code/#releases--versioning) гэж гаргачихвал).

CI скриптүүд хөгжүүлэгчийн машинаас тусдаа ажилладаг тул удаан ажилладаг ажлуудыг
тэнд хялбар ажиллуулж болно. Жишээ нь янз бүрийн үйлдлийн систем, хэлний
хувилбаруудын хослол (matrix) дээр тест ажиллуулж, програм тань бүгд дээр нь зөв
ажиллаж байгааг баталгаажуулж болно.

Ерөнхийдөө CI дээрх скриптүүд кодыг тань өөрчилдөггүй: хэрэгслүүдийг "засах"
горимоор биш "шалгах" горимоор ажиллуулдаг, жишээ нь код форматлагдаагүй байвал
алдаа заагаад зогсдог.

Репонууд README-дээ CI-ийн төлөв, кодын хамрах хүрээ гэх мэт мэдээллийг харуулсан
[төлөвийн тэмдэг (status badge)](https://docs.github.com/en/actions/how-tos/monitor-workflows/add-a-status-badge)
байршуулдаг. Жишээ нь доор Missing Semester-ийн одоогийн угсралтын (build) төлөв байна.

[![Build Status](https://github.com/missing-semester/missing-semester/actions/workflows/build.yml/badge.svg)](https://github.com/missing-semester/missing-semester/actions/workflows/build.yml) [![Links Status](https://github.com/missing-semester/missing-semester/actions/workflows/links.yml/badge.svg)](https://github.com/missing-semester/missing-semester/actions/workflows/links.yml)

> Манай [холбоос шалгагч](https://github.com/missing-semester/missing-semester/blob/master/.github/workflows/links.yml)
> [proof-html](https://github.com/anishathalye/proof-html) GitHub Action ашигладаг
> бөгөөд гадны вэбсайтуудын асуудлаас болж байнга алдаа заадаг. Гэсэн ч олон эвдэрсэн
> холбоос олж засахад тусалсан (заримдаа үсгийн алдаанаас, ихэнхдээ вэбсайтууд
> агуулгаа зөөхдөө чиглүүлэлт тавиагүй эсвэл бүр алга болсноос).

CI үйлчилгээ, форматлагч, линтер, тестийн сангуудын онцлогийг сурах хамгийн сайн арга
бол жишээнээс суралцах. GitHub дээрээс чанартай нээлттэй эхийн төслүүд олоод
(хэл, чиглэл, хэмжээ, хамрах хүрээгээрээ таны төсөлтэй ойр байх тусмаа сайн),
тэдгээрийн `pyproject.toml`, `.github/workflows/`, `DEVELOPMENT.md` болон бусад
холбогдох файлуудыг судлаарай.

## Тасралтгүй deploy (continuous deployment)

Тасралтгүй deploy гэдэг нь CI-ийн дэд бүтцийг ашиглаж өөрчлөлтүүдийг бодитоор
*deploy хийх* явдал. Жишээ нь Missing Semester-ийн репо GitHub Pages руу тасралтгүй
deploy хийдэг тул лекцийн тэмдэглэлээ шинэчлээд `git push` хийх бүрд сайт автоматаар
build хийгдэж нийтлэгдэнэ. Мөн CI дээр програмын binary, үйлчилгээний Docker image
гэх мэт бусад [бүтээгдэхүүнүүдийг](/2026/shipping-code/) (artifact) үүсгэж болно.

# Команд ажиллуулагч {#command-runners}

[just](https://github.com/casey/just) гэх мэт команд ажиллуулагч төслийн хүрээнд
командуудыг ажиллуулахыг хялбарчилдаг. Төслийнхөө кодын чанарын дэд бүтцийг
боловсруулж байхдаа хөгжүүлэгчдээр `uv run ruff check --fix` шиг урт командуудыг
цээжлүүлэхийг хүсэхгүй байх. Команд ажиллуулагчаар үүнийг `just lint` болгоод,
хөгжүүлэгчийн ажиллуулах хэрэгтэй бусад хэрэгслүүдэд `just format`, `just typecheck`
гэх мэт товч нэр өгч болно.

Зарим хэлний төсөл эсвэл багц менежер ийм боломжийг өөртөө агуулдаг тул `just`
шиг хэлнээс хамааралгүй хэрэгсэл заавал хэрэггүй. Жишээ нь Node.js-ийн
[npm](https://nodejs.org/en/learn/getting-started/an-introduction-to-the-npm-package-manager)-ийн
`package.json` доторх `scripts` хэсэг, Python-ы [Hatch](https://hatch.pypa.io/)-ийн
`pyproject.toml` доторх `tool.hatch.envs.*.scripts` хэсэг ийм боломж олгодог.

# Regular expression {#regular-expressions}

*Regular expression*, товчоор "regex" бол тэмдэгт мөрүүдийн олонлогийг илэрхийлэх
жижиг хэл. Regex-ийн хэв загварыг командын мөрийн хэрэгсэл, IDE гэх мэт олон газарт
таарц хайхад хэрэглэдэг. Жишээ нь [ag](https://github.com/ggreer/the_silver_searcher)
бүх кодоос regex-ээр хайх боломжтой (жишээ нь `ag "import .* as .*"` Python-ы өөр
нэрээр оруулсан бүх import-ыг олно), [go test](https://pkg.go.dev/cmd/go#hdr-Test_packages)
`-run [regexp]` сонголтоор тестүүдээ шүүж ажиллуулдаг. Мөн програмчлалын хэлнүүд
regex-ийн суурь эсвэл гадны сантай байдаг тул таарц хайх, шалгах, задлан шинжлэхэд
regex хэрэглэж болно.

Ойлгоход туслах үүднээс хэдэн жишээ авъя. Энэ лекцэд
[Python-ы regex синтакс](https://docs.python.org/3/library/re.html) хэрэглэнэ.
Regex-ийн олон "аялга" (flavor) бий, ялангуяа нарийн боломжууд дээрээ бага зэрэг
ялгаатай. Regex-ээ туршиж, алдааг нь олохдоо [regex101](https://regex101.com/) шиг
онлайн хэрэгсэл ашиглаж болно.

- `abc` --- "abc"-тэй яг таарна.
- `missing|semester` --- "missing" эсвэл "semester"-тэй таарна.
- `\d{4}-\d{2}-\d{2}` --- "2026-01-14" гэх мэт ЖЖЖЖ-СС-ӨӨ форматтай огноотой
  таарна. Гэхдээ энэ нь дөрвөн цифр, зураас, хоёр цифр, зураас, хоёр цифр байгааг
  л шалгадаг, огноо өөрөө зөв эсэхийг шалгадаггүй тул "2026-01-99" ч таарна.
- `.+@.+` --- имэйл хаягтай таарна: хэдэн тэмдэгт, "@", дахиад хэдэн тэмдэгт.
  Энэ бол хамгийн энгийн шалгалт, "nonsense@@@email" шиг мөр ч таарна. Имэйл хаягийг
  ямар ч алдаагүй шалгадаг regex [байдаг](https://pdw.ex-parrot.com/Mail-RFC822-Address.html)
  ч бодит амьдралд хэрэглэхэд хэтэрхий нүсэр.

## Regex-ийн синтакс

Regex-ийн синтаксын бүрэн тайлбарыг [энэ баримт бичгээс](https://docs.python.org/3/library/re.html#regular-expression-syntax)
(эсвэл бусад онлайн материалаас) харж болно. Үндсэн бүрэлдэхүүнүүд:

- `abc` тусгай утгагүй тэмдэгтүүд бол тухайн мөртэй яг таарна (энд "abc")
- `.` дурын нэг тэмдэгттэй таарна
- `[abc]` хаалтан доторх тэмдэгтүүдийн аль нэгтэй таарна ("a", "b", эсвэл "c")
- `[^abc]` хаалтан дотор байхгүй дурын тэмдэгттэй таарна (жишээ нь "d")
- `[a-f]` мужид багтах дурын тэмдэгттэй таарна (жишээ нь "c", гэхдээ "q" биш)
- `a|b` аль нэг хэв загвартай таарна (жишээ нь "a" эсвэл "b")
- `\d` дурын цифртэй таарна (жишээ нь "3")
- `\w` үгийн тэмдэгттэй таарна (жишээ нь "x")
- `\b` үгийн *хил*-тэй (word boundary) таарна (жишээ нь "missing semester"-д
  "m"-ийн өмнө, "g"-ийн дараа, "s"-ийн өмнө, "r"-ийн дараа)
- `(...)` хэв загварыг бүлэг болгоно
- `...?` хэв загвар 0 эсвэл 1 удаа орохтой таарна, жишээ нь `words?` нь "word"
  эсвэл "words"-тэй таарна
- `...*` хэдэн ч удаа орохтой таарна, жишээ нь `.*` дурын тэмдэгтүүдийн дурын
  урттай мөртэй таарна
- `...+` 1 буюу түүнээс олон удаа орохтой таарна, жишээ нь `\d+` дор хаяж нэг
  цифртэй таарна
- `...{N}` яг N удаа давтагдахтай таарна, жишээ нь `\d{4}` 4 оронтой тоотой таарна
- `\.` жинхэнэ "."-тэй таарна
- `\\` жинхэнэ "\\"-тэй таарна
- `^` мөрийн эхлэлтэй таарна
- `$` мөрийн төгсгөлтэй таарна

## Бүлэг барих ба буцааж дуудах

Regex-д `(...)` бүлэг хэрэглэвэл таарцын тэр хэсгийг тусад нь авах, эсвэл
хайж солихдоо ашиглаж болно. Жишээ нь ЖЖЖЖ-СС-ӨӨ огнооноос зөвхөн сарыг авахдаа
Python-д:

```python
>>> import re
>>> re.match(r"\d{4}-(\d{2})-\d{2}", "2026-01-14").group(1)
'01'
```

Засварлагч дээрээ хайж солихдоо барьсан бүлгүүдээ буцааж дуудаж болно. Синтакс нь
IDE бүрд өөр: жишээ нь VS Code-д `$1`, `$2`, Vim-д `\1`, `\2` гэж бичдэг.

## Хязгаарлалт

[Регуляр хэлнүүд](https://en.wikipedia.org/wiki/Regular_language) хүчтэй ч
хязгаартай; стандарт regex-ээр илэрхийлж чадахгүй тэмдэгт мөрийн ангиуд бий (жишээ
нь {a^n b^n \| n &ge; 0}, өөрөөр хэлбэл хэдэн "a"-ийн араас яг тийм тооны "b"
орсон мөрүүдийн олонлогтой таарах regex бичих [боломжгүй](https://en.wikipedia.org/wiki/Pumping_lemma_for_regular_languages);
практик жишээ гэвэл HTML регуляр хэл биш). Бодит байдал дээр орчин үеийн regex-ийн
хөдөлгүүрүүд lookahead, backreference гэх мэт регуляр хэлнээс давсан боломж
дэмждэг, эдгээр нь их хэрэгтэй, гэхдээ илэрхийлэх чадвар нь хязгаартай хэвээр гэдгийг
мэдэж байх нь чухал. Илүү нарийн хэлийг задлан шинжлэхэд илүү чадвартай parser
хэрэг болно (нэг жишээ нь [PEG](https://en.wikipedia.org/wiki/Parsing_expression_grammar)
parser болох [pyparsing](https://github.com/pyparsing/pyparsing)).

## Regex сурах нь

Энэ хэлний бүх юмыг цээжлэх гэж зүтгэх хэрэггүй. Үндсэн ойлголтуудыг (энэ лекцээр
үзсэн зүйлс) аваад, хэрэг гарах бүрд баримт бичгээ харж байхад хангалттай.

AI-тай ярилцдаг хэрэгслүүд regex бичихэд их тустай. Жишээ нь дуртай LLM-дээ ийм
промпт өгөөд үзээрэй:

```
Write a Python-style regex pattern that matches the requested path from log lines from Nginx. Here is an example log line:

169.254.1.1 - - [09/Jan/2026:21:28:51 +0000] "GET /feed.xml HTTP/2.0" 200 2995 "-" "python-requests/2.32.3"
```

1. Ажиллаж буй төсөлдөө форматлагч, линтер, pre-commit hook тохируулаарай. Олон
   алдаа гарвал: форматын алдааг автомат форматлагч засна. Линтерийн алдааг засахдаа
   [AI агент](/2026/agentic-coding/) ашиглаад үзээрэй. Агент линтерийг өөрөө
   ажиллуулж, үр дүнг нь харж, алдаа бүгд засагдтал давтан ажиллаж чадахаар
   тохируулаарай. AI кодыг тань эвдээгүй эсэхийг сайтар шалгаарай!

1. Мэддэг хэлнийхээ тестийн сантай танилцаад, ажиллаж буй төсөлдөө unit тест
   бичээрэй. Coverage хэрэгсэл ажиллуулж HTML тайлан гаргаад үзээрэй. Кодын аль
   мөрүүд хамрагдсаныг харж чадаж байна уу? Хамрах хүрээ тань магадгүй маш бага
   байх. Хэдэн тест гараараа бичиж сайжруулаад үзээрэй. Дараа нь
   [AI агент](/2026/agentic-coding/)-аар хамрах хүрээг (coverage) сайжруулаарай; агент
   тестүүдийг хамрах хүрээний хэмжилттэй нь ажиллуулж, мөр бүрийн тайлан гаргаж чадаж байгааг
   шалгаарай, ингэвэл хаана анхаарахаа мэднэ. AI-ийн бичсэн тестүүд үнэхээр сайн
   байна уу?

1. Ажиллаж буй төсөлдөө push хийх бүрд ажилладаг CI тохируулаарай. CI-д форматын
   шалгалт, линтер, тестүүдийг ажиллуулаарай. Кодоо зориуд эвдээд (жишээ нь
   линтерийн дүрэм зөрчсөн код нэмээд) CI үүнийг барьж байгааг шалгаарай.

1. [Regex](#regular-expressions) бичээд, [командын мөрийн хэрэгсэл](/2026/course-shell/)
   болох `grep`-ээр кодоосоо `subprocess.Popen(..., shell=True)` дуудлагуудыг
   олоорой. Одоо regex-ээ "эвдэх" гээд үзээрэй. Grep-ийг тань хуурч чадсан аюултай
   кодыг [semgrep](#linting) олж чадсаар байна уу?

1. [Энэ лекцийн тэмдэглэл](https://raw.githubusercontent.com/missing-semester/missing-semester/refs/heads/master/_2026/code-quality.md)
   доторх `-` [Markdown жагсаалтын тэмдэгтийг](https://spec.commonmark.org/0.31.2/#bullet-list-marker)
   `*`-оор солиж, IDE эсвэл засварлагч дээрээ regex-ээр хайж солихыг дадлагажуулаарай.
   Файл доторх бүх "-"-ийг шууд солих нь буруу гэдгийг анхаараарай: тэр тэмдэгт
   жагсаалтын тэмдэгтээс өөр олон газар хэрэглэгдсэн.

1. `{"name": "Alyssa P. Hacker", "college": "MIT"}` хэлбэрийн JSON-оос нэрийг

   оролдлогоор `Alyssa P. Hacker", "college": "MIT`-ийг сугалдаг regex бичиж
   магадгүй; яаж засахыг мэдэхийн тулд [Python-ы regex баримт бичиг](https://docs.python.org/3/library/re.html)-ээс

    1. Нэр нь өөрөө `"` агуулсан байсан ч (JSON-д давхар хашилтыг `\"` гэж
       бичдэг) ажилладаг болгож засаарай.
    1. Бодит амьдрал дээр нарийн задлан шинжлэх ажилд regex хэрэглэхийг бид
       **зөвлөдөггүй**. Хэрэглэдэг хэлнийхээ JSON задлагчийг яаж хэрэглэхийг олж

       Python-д `import json`-оос гадна ганцхан мөр кодоор хийж болно.
