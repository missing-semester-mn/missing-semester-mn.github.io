Кодоо өөрийн машин дээр ажиллуулах нэг хэрэг. Харин өөр хүний машин, сервер,
эсвэл бодит хэрэглэгчидтэй орчин (production) дээр найдвартай ажиллуулах бол бүр
өөр асуудал.

Кодыг хүргэх (shipping) гэдэг нь бичсэн кодоо өөр хүн таны зөөврийн компьютерийн
тохиргоог яг давтахгүйгээр ажиллуулж чадах, хэрэглэхэд бэлэн хэлбэрт оруулахыг
хэлнэ. Энэ нь хэл, системийн сан, үйлдлийн систем, хаана ажиллуулах гээд олон
зүйлээс хамаарна. Сан, командын мөрийн хэрэгсэл, вэб үйлчилгээ гурав тус бүр өөр
шаардлагатай. Гэхдээ гол асуулт нь адилхан: эцэст нь хүргэх _бүтээгдэхүүн_
(artifact) маань яг юу вэ, түүнийг ажиллуулахын тулд орчноос юу шаардах вэ?

Энэ лекцээр дараах сэдвүүдийг үзнэ:

- [Бүтээгдэхүүн ба багцлалт](#artifacts--packaging)
- [Хувилбар гаргах ба дугаарлах](#releases--versioning)

Жишээнүүдийг Python-ы экосистем дээр тайлбарлана. Бусад хэлэнд хэрэгслүүдийн нэр,
формат өөр байж болох ч үндсэн санаа нь ихэнхдээ адилхан.

# Хамаарал ба орчин {#dependencies--environments}

Орчин үеийн програм хангамж олон давхар хийсвэрлэл дээр тогтдог. Програмууд
логикийнхоо нэг хэсгийг бусад сан, үйлчилгээнд даатгах нь түгээмэл. Ингэхэд
таны програм болон түүнд хэрэгтэй сангуудын хооронд _хамаарал_ (dependency) үүснэ.
Жишээ нь Python дээр вэбсайтын агуулгыг татахдаа ихэвчлэн ингэж бичдэг:

```python
import requests

response = requests.get("https://missing.csail.mit.edu")
```

Гэхдээ `requests` сан Python-той хамт суудаггүй. Тиймээс суулгалгүйгээр энэ кодыг
ажиллуулбал Python алдаа заана:

```console
$ python fetch.py
Traceback (most recent call last):
  File "fetch.py", line 1, in <module>
    import requests
ModuleNotFoundError: No module named 'requests'
```

Энэ санг ашиглахын тулд эхлээд `pip install requests`-ээр суулгах хэрэгтэй.
`pip` бол Python-ы багц суулгадаг командын мөрийн хэрэгсэл. `pip install requests`
ажиллуулахад цаана нь ерөнхийдөө ийм алхмууд хийгдэнэ:

1. Python-ы багцын сангаас ([PyPI](https://pypi.org/)) `requests`-ийг хайна.
1. Таны платформд тохирох бүтээгдэхүүнийг (artifact) хайна.
1. Хамаарлуудыг шийднэ --- `requests` өөрөө бусад багцаас хамаардаг тул суулгагч
   тэдгээр дам хамаарлуудын тохирох хувилбаруудыг олж, түрүүлж суулгах ёстой.
1. Бүтээгдэхүүнүүдийг татаж, задлаад файлын системийн зөв газар руу хуулна.

```console
$ pip install requests
Collecting requests
  Downloading requests-2.32.3-py3-none-any.whl (64 kB)
Collecting charset-normalizer<4,>=2
  Downloading charset_normalizer-3.4.0-cp311-cp311-manylinux_x86_64.whl (142 kB)
Collecting idna<4,>=2.5
  Downloading idna-3.10-py3-none-any.whl (70 kB)
Collecting urllib3<3,>=1.21.1
  Downloading urllib3-2.2.3-py3-none-any.whl (126 kB)
Collecting certifi>=2017.4.17
  Downloading certifi-2024.8.30-py3-none-any.whl (167 kB)
Installing collected packages: urllib3, idna, charset-normalizer, certifi, requests
Successfully installed certifi-2024.8.30 charset-normalizer-3.4.0 idna-3.10 requests-2.32.3 urllib3-2.2.3
```

Эндээс `requests`-д `certifi`, `charset-normalizer` гэх мэт өөрийн хамаарлууд
байгааг, тэдгээрийг `requests`-ээс өмнө суулгах ёстойг харж болно. Суулгасны
дараа Python `import` хийхдээ санг олж чадна.

```console
$ python -c 'import requests; print(requests.__path__)'
['/usr/local/lib/python3.11/dist-packages/requests']

$ pip list | grep requests
requests        2.32.3
```

Програмчлалын хэл бүр сан суулгах, нийтлэх өөрийн хэрэгсэл, стандарт, арга
барилтай. Rust шиг зарим хэлэнд бүгд нэг хэрэгсэлд нэгдсэн --- `cargo` угсрах,
тест ажиллуулах, хамаарал удирдах, нийтлэх бүх ажлыг хариуцна. Харин Python шиг
хэлэнд нэгдэл нь стандартын түвшинд хийгддэг: ганц хэрэгслийн оронд багцлах
үйл явцыг тодорхойлсон стандартууд бий. Үүний ачаар ажил бүрд өрсөлдөгч олон
хэрэгсэл гарч ирдэг (`pip`-ийн оронд [`uv`](https://docs.astral.sh/uv/),
`setuptools`-ийн оронд [`hatch`](https://hatch.pypa.io/) эсвэл
[`poetry`](https://python-poetry.org/)). LaTeX шиг зарим экосистемд TeX Live,
MacTeX гэх мэт түгээлтүүд олон мянган багцыг урьдчилан суулгачихсан ирдэг.

Хамаарал нэмэх тусам хамаарлын зөрчил гарах эрсдэл нэмэгдэнэ. Зөрчил гэдэг нь
хоёр програм нэг хамаарлын хоорондоо үл нийцэх хувилбарыг шаардахыг хэлнэ.
Жишээ нь `tensorflow==2.3.0` нь `numpy>=1.16.0,<1.19.0`-ийг, `pandas==1.2.0` нь
`numpy>=1.16.5`-ийг шаардвал `numpy>=1.16.5,<1.19.0`-д багтах дурын хувилбар
тохирно. Гэтэл төслийн өөр нэг багц `numpy>=1.19` шаардвал бүх хязгаарыг зэрэг
хангах хувилбар байхгүй тул зөрчил үүснэ.

Олон багц дундын хамаарлынхаа үл нийцэх хувилбаруудыг шаардах энэ байдлыг
_dependency hell_ (хамаарлын там) гэдэг. Үүнийг шийдэх нэг арга бол програм бүрийн
хамаарлыг тусдаа _орчинд_ (environment) тусгаарлах.

Python дээр виртуал орчин (virtual environment) ингэж үүсгэнэ:

```console
$ which python
/usr/bin/python
$ pwd
/home/missingsemester
$ python -m venv venv
$ source venv/bin/activate
$ which python
/home/missingsemester/venv/bin/python
$ which pip
/home/missingsemester/venv/bin/pip
$ python -c 'import requests; print(requests.__path__)'
['/home/missingsemester/venv/lib/python3.11/site-packages/requests']

$ pip list
Package Version
------- -------
pip     24.0
```

Орчныг тухайн хэлний ажиллах орчны бие даасан хувилбар, өөрийн гэсэн суулгасан
багцуудтай гэж ойлгож болно. Виртуал орчин буюу venv хамаарлуудыг системийн
Python-оос тусгаарлана. Төсөл бүрд хэрэгтэй хамаарлуудтай нь тусдаа виртуал
орчин үүсгэж хэвшээрэй.

> Орчин үеийн олон үйлдлийн систем Python зэрэг хэлний ажиллах орчинтой хамт
> ирдэг, гэхдээ тэднийг өөрчлөх эрсдэлтэй: үйлдлийн систем өөрөө тэдгээрт
> тулгуурладаг байж магадгүй. Тиймээс үргэлж тусдаа орчин үүсгэж хэрэглээрэй.

Зарим хэлэнд суулгах үйл явцыг тодорхой хэрэгсэл биш, стандарт тодорхойлдог.
Python-д [PEP 517](https://peps.python.org/pep-0517/) угсралтын системийн
интерфейсийг, [PEP 621](https://peps.python.org/pep-0621/) төслийн мета өгөгдлийг
`pyproject.toml`-д хэрхэн хадгалахыг заадаг. Энэ стандартын ачаар `pip`-ээс
хамаагүй хурдан `uv` шиг хэрэгслүүд гарч ирсэн. `uv`-ийг суулгахад `pip install uv`
хангалттай.

`uv` нь `pip`-тэй ижил интерфейстэй ч хамаагүй хурдан:

```console
$ uv pip install requests
Resolved 5 packages in 12ms
Prepared 5 packages in 0.45ms
Installed 5 packages in 8ms
 + certifi==2024.8.30
 + charset-normalizer==3.4.0
 + idna==3.10
 + requests==2.32.3
 + urllib3==2.2.3
```

> Боломжтой бол `pip`-ийн оронд `uv pip` хэрэглээд үзээрэй. Суулгах хугацааг
> мэдэгдэхүйц хэмнэнэ.

Орчин хамаарлыг тусгаарлахаас гадна хэлнийхээ өөр өөр хувилбарыг зэрэг ашиглах
боломж өгдөг:

```console
$ uv venv --python 3.12 venv312
Using CPython 3.12.7
Creating virtual environment at: venv312

$ source venv312/bin/activate && python --version
Python 3.12.7

$ uv venv --python 3.11 venv311
Using CPython 3.11.10
Creating virtual environment at: venv311

$ source venv311/bin/activate && python --version
Python 3.11.10
```

Кодоо Python-ы олон хувилбар дээр шалгах, эсвэл төсөл тань тодорхой хувилбар
шаарддаг үед энэ их хэрэгтэй.

> Зарим хэлэнд виртуал орчныг гараар үүсгэх шаардлагагүй, төсөл бүр өөрийн
> хамаарлын орчинтой автоматаар болдог, гэхдээ зарчим нь адилхан. Орчин үеийн
> ихэнх хэл нэг машин дээр хэлнийхээ олон хувилбарыг удирдаж, төсөл бүрд аль
> хувилбарыг ашиглахаа зааж өгөх боломжтой болсон.

# Бүтээгдэхүүн ба багцлалт {#artifacts--packaging}

Програм хангамжийн хөгжүүлэлтэд эх код (source code), бүтээгдэхүүн (artifact) хоёрыг
ялгаж үздэг. Хөгжүүлэгчид эх кодыг бичиж, уншдаг бол бүтээгдэхүүн нь тэр эх кодоос
гаргаж авсан, суулгах эсвэл байршуулахад бэлэн, багцалсан үр дүн юм.
Бүтээгдэхүүн нь ганц кодын файл ч байж болно, програм ажиллахад хэрэгтэй бүх
зүйлийг багтаасан бүхэл бүтэн виртуал машин ч байж болно.
Жишээ болгож одоогийн хавтас дахь `greet.py` Python файлыг авч үзье:

```console
$ cat greet.py
def greet(name):
    return f"Hello, {name}!"

$ python -c "from greet import greet; print(greet('World'))"
Hello, World!

$ cd /tmp
$ python -c "from greet import greet; print(greet('World'))"
ModuleNotFoundError: No module named 'greet'
```

Өөр хавтас руу шилжихэд import амжилтгүй болж байгаа нь Python модулиудыг
зөвхөн тодорхой газраас хайдагтай холбоотой: одоогийн хавтас, суулгасан
багцууд, мөн `PYTHONPATH` дахь замууд. Багцлах нь кодыг Python-ы мэддэг
байршилд суулгаж өгснөөр энэ асуудлыг шийддэг.

Python-д сан багцлах гэдэг нь `pip`, `uv` гэх мэт багц суулгагчийн ашиглаж чадах
бүтээгдэхүүнийг бэлтгэхийг хэлнэ. Python-ы бүтээгдэхүүнийг _wheel_ гэдэг. Wheel
багц суулгахад хэрэгтэй бүх мэдээллийг агуулна: кодын файлууд, багцын мета өгөгдөл
(нэр, хувилбар, хамаарлууд), файлуудыг хаана байрлуулах заавар. Бүтээгдэхүүн
угсрахын тулд төслийн мэдээлэл, хамаарал, хувилбар зэргийг агуулсан төслийн
файл (манифест) бичих хэрэгтэй. Python-д үүнд `pyproject.toml` хэрэглэнэ.

> `pyproject.toml` бол орчин үеийн, зөвлөж буй арга. Хуучин `requirements.txt`,
> `setup.py` хоёр одоо ч дэмжигддэг ч боломжтой бол `pyproject.toml`-ийг сонгоорой.

Командын мөрийн хэрэгсэлтэй сангийн хамгийн энгийн `pyproject.toml` жишээ ийм:

```toml
[project]
name = "greeting"
version = "0.1.0"
description = "A simple greeting library"
dependencies = ["typer>=0.9"]

[project.scripts]
greet = "greeting:cli"

[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"
```

`typer` бол маш бага кодоор командын мөрийн интерфейс хийхэд өргөн хэрэглэгддэг
Python-ы сан.

Мөн үүнд тохирох `greeting.py` файл:

```python
import typer


def greet(name: str) -> str:
    return f"Hello, {name}!"


def cli():
    typer.run(greet)


if __name__ == "__main__":
    cli()
```

Одоо wheel-ээ угсарч болно:

```console
$ uv build
Building source distribution...
Building wheel from source distribution...
Successfully built dist/greeting-0.1.0.tar.gz
Successfully built dist/greeting-0.1.0-py3-none-any.whl

$ ls dist/
greeting-0.1.0-py3-none-any.whl
greeting-0.1.0.tar.gz
```

`.whl` файл бол wheel өөрөө (тодорхой бүтэцтэй zip архив). `.tar.gz` бол эх
кодноос угсрах шаардлагатай системүүдэд зориулсан эх кодын багц (source
distribution).

Багцад юу орсныг wheel-ийн агуулгаас харж болно:

```console
$ unzip -l dist/greeting-0.1.0-py3-none-any.whl
Archive:  dist/greeting-0.1.0-py3-none-any.whl
  Length      Date    Time    Name
---------  ---------- -----   ----
      150  2024-01-15 10:30   greeting.py
      312  2024-01-15 10:30   greeting-0.1.0.dist-info/METADATA
       92  2024-01-15 10:30   greeting-0.1.0.dist-info/WHEEL
        9  2024-01-15 10:30   greeting-0.1.0.dist-info/top_level.txt
      435  2024-01-15 10:30   greeting-0.1.0.dist-info/RECORD
---------                     -------
      998                     5 files
```

Энэ wheel-ийг өөр хүнд өгвөл тэр ингэж суулгана:

```console
$ uv pip install ./greeting-0.1.0-py3-none-any.whl
$ greet Alice
Hello, Alice!
```

Ингэснээр бидний угсарсан сан, доторх `greet` хэрэгсэлтэйгээ хамт тэр хүний орчинд
сууна.

Энэ аргад хязгаар бий. Жишээ нь сан тань GPU-д зориулсан CUDA шиг тодорхой
платформын сангаас хамаардаг бол бүтээгдэхүүн тань зөвхөн тэр сангууд суусан
систем дээр л ажиллана. Тэгвэл үйлдлийн систем, архитектур бүрд тусдаа wheel
угсрах хэрэгтэй болно.

Програм суулгахдаа эх кодоос суулгах (installing from source), бэлэн бинари
суулгах (installing a prebuilt binary) хоёрын ялгаа их. Эх кодоос суулгана гэдэг
нь кодыг татаж аваад өөрийн машин дээр хөрвүүлэхийг хэлнэ --- хөрвүүлэгч,
угсралтын хэрэгслүүд хэрэгтэй, том төсөлд их удаан болж магадгүй.

Харин бэлэн бинари суулгах нь өөр хүний аль хэдийн хөрвүүлсэн бүтээгдэхүүнийг
татаж авах --- хурдан, амар, гэхдээ таны үйлдлийн систем, архитектурт яг таарах
ёстой. Жишээ нь [ripgrep-ийн хувилбаруудын хуудас](https://github.com/BurntSushi/ripgrep/releases)
дээр Linux, macOS, Windows-д зориулсан бэлэн бинари файлууд (prebuilt binaries)
бий.

# Хувилбар гаргах ба дугаарлах {#releases--versioning}

Код бичих ажил тасралтгүй үргэлжилдэг ч хэрэглэгчдэд тодорхой үечлэлтэйгээр
хувилбар болж гардаг. Хөгжүүлэлтийн орчин (dev environment), бодит орчин
(production environment) хоёрын хооронд тод зааг бий. Кодыг бодит орчинд
*гаргахаас* өмнө хөгжүүлэлтийн орчинд зөв ажиллаж байгааг нь батлах хэрэгтэй.
Хувилбар гаргах (release) нь тест, хамаарлын удирдлага, дугаарлалт, тохиргоо,
байршуулалт, нийтлэх гэх мэт олон алхамтай.

Сангууд нэг байрандаа зогсдоггүй: алдаа нь засагдаж, шинэ боломж нэмэгдэж
байнга хөгждөг. Энэ хөгжлийг сангийн тухайн үеийн төлөвт оноосон хувилбарын
дугаараар хянадаг. Сангийн өөрчлөлт жижиг засвар (patch), шинэ боломж (feature),
эсвэл өмнөх хувилбартай нийцэхгүй том өөрчлөлт (breaking change) байж болно.
Өөрчлөлтийн бүртгэл (changelog) хувилбар бүрт юу өөрчлөгдсөнийг бичдэг; хөгжүүлэгчид
шинэ хувилбарт юу орсныг үүгээр мэдэгддэг.

Гэхдээ хамаарал бүрийн өөрчлөлтийг нэг бүрчлэн хянах боломжгүй, дам хамаарлуудыг
(transitive dependencies) тооцвол бүр хэцүү.

> Төслийнхөө хамаарлын модыг `uv tree`-ээр харж болно. Бүх багц, тэдгээрийн
> дам хамаарлуудыг модон хэлбэрээр харуулна.

Үүнийг хялбарчлахын тулд хувилбар дугаарлах дүрмүүд бий. Хамгийн өргөн
хэрэглэгддэг нь [Семантик хувилбарлалт](https://semver.org/) буюу SemVer.
SemVer-ийн дагуу хувилбарын дугаар MAJOR.MINOR.PATCH хэлбэртэй. Товчхондоо:

- PATCH (жишээ нь 1.2.3 → 1.2.4) зөвхөн алдааны засвартай, өмнөх хувилбартай бүрэн
  нийцнэ.
- MINOR (жишээ нь 1.2.3 → 1.3.0) өмнөх хувилбартай нийцтэйгээр шинэ боломж нэмнэ.
- MAJOR (жишээ нь 1.2.3 → 2.0.0) өмнөх хувилбартай нийцэхгүй, кодоо өөрчлөх
  шаардлагатай өөрчлөлтийг (breaking change) заана.

> Энэ бол маш хялбаршуулсан тайлбар. Жишээ нь 0.1.3-аас 0.2.0 руу шилжихэд яагаад
> нийцэл эвдэрч болох, 1.0.0-rc.1 гэж юу болохыг ойлгохын тулд SemVer-ийн бүрэн
> тодорхойлолтыг уншаарай.

Python-ы багцлалт семантик хувилбарлалтыг шууд дэмждэг тул хамаарлын хувилбарыг
янз бүрийн нөхцөлөөр зааж болно. `pyproject.toml`-д нийцтэй хувилбаруудын мужийг
ингэж хязгаарлана:

```toml
[project]
dependencies = [
    "requests==2.32.3",  # Exact version - only this specific version
    "click>=8.0",        # Minimum version - 8.0 or newer
    "numpy>=1.24,<2.0",  # Range - at least 1.24 but less than 2.0
    "pandas~=2.1.0",     # Compatible release - >=2.1.0 and <2.2.0
]
```

Хувилбар заагчид багц менежер бүрд (npm, cargo гэх мэт) арай өөр утгатай. Python-д
`~=` нь "нийцтэй хувилбар" гэсэн үг --- `~=2.1.0` бол "2.1.0-тай нийцэх дурын
хувилбар", өөрөөр хэлбэл `>=2.1.0` ба `<2.2.0`. Энэ нь npm, cargo-ийн SemVer-т
нийцэх хувилбарыг заадаг карет (`^`) оператортой бараг адилхан.

Бүх програм семантик хувилбарлалт хэрэглэдэггүй. Бас нэг түгээмэл арга бол
хуанлийн хувилбарлалт (CalVer): дугаар нь утгаас илүү гарсан огноогоо илэрхийлдэг.
Жишээ нь Ubuntu `24.04` (2024 оны 4-р сар), `24.10` (2024 оны 10-р сар) гэж
дугаарладаг. CalVer-ээр хувилбар хэр хуучныг амархан харна, гэхдээ нийцлийн
талаар юу ч хэлэхгүй. Эцэст нь, семантик хувилбарлалт ч алдаагүй биш: хөгжүүлэгчид
заримдаа санамсаргүй MINOR эсвэл PATCH хувилбарт нийцэл эвдэх өөрчлөлт оруулчихдаг.

# Дахин давтагдах байдал {#reproducibility}

Таны код олон давхар хийсвэрлэл дээр ажилладаг: хэлний ажиллах орчин, бусдын
сангууд, үйлдлийн систем, бүр тоног төхөөрөмж хүртэл. Эдгээрийн аль нэгэнд гарсан
өчүүхэн ялгаа ч кодын ажиллагааг өөрчилж, бүр эвдэж болно. Тоног төхөөрөмжийн
ялгаа хүртэл кодоо хүргэхэд нөлөөлдөг.

Хувилбар "тогтоох" (pinning) гэдэг нь муж биш, яг тодорхой хувилбар зааж өгөхийг
хэлнэ (жишээ нь `requests>=2.0`-ийн оронд `requests==2.32.3`).

Багц менежерийн нэг ажил бол хамаарал, дам хамаарлуудын бүх хязгаарыг тооцоод,
бүгдийг нь хангах хувилбаруудын жагсаалт гаргах. Дараа нь яг ижилхэн суулгаж
болохын тулд энэ жагсаалтыг файлд хадгалдаг. Үүнийг _lock файл_ гэдэг.

```console
$ uv lock
Resolved 12 packages in 45ms

$ cat uv.lock | head -20
version = 1
requires-python = ">=3.11"

[[package]]
name = "certifi"
version = "2024.8.30"
source = { registry = "https://pypi.org/simple" }
sdist = { url = "https://files.pythonhosted.org/...", hash = "sha256:..." }
wheels = [
    { url = "https://files.pythonhosted.org/...", hash = "sha256:..." },
]
...
```

Хувилбар заах, дахин давтагдах байдлын (reproducibility) хувьд анхаарах нэг чухал
ялгаа бол сан ба програм/үйлчилгээ. Сан бусдын кодонд импортлогдож хэрэглэгддэг,
тэр код өөрийн гэсэн хамааралтай байж болно. Тиймээс сан хувилбарыг хэт хатуу
заавал хэрэглэгчийн бусад хамааралтай зөрчилдөнө. Харин програм, үйлчилгээ бол
хэлхээний эцэст байдаг: тэд програмчлалын интерфейсээр биш, хэрэглэгчийн
интерфейс (UI) эсвэл API-аар үйлчилдэг. Тиймээс санд хувилбарын муж заах нь
экосистемтэй эвтэй ажиллахад тусалдаг бол програмд яг тодорхой хувилбар тогтоох нь
дахин давтагдах байдлыг хангана --- програмыг ажиллуулж буй хүн бүр яг ижил
хамаарлуудыг хэрэглэнэ.

Дээд зэргийн дахин давтагдах байдал шаарддаг төсөлд [Nix](https://nixos.org/),
[Bazel](https://bazel.build/) шиг хэрэгслүүд _битүү угсралт_ (hermetic build) хийдэг:
хөрвүүлэгч, системийн сан, бүр угсралтын орчин хүртэл тогтоосон байдаг. Ингэснээр
хэзээ, хаана угсарсан ч байт бүрээрээ яг ижил үр дүн гарна.

> NixOS-ээр компьютерийнхээ бүх тохиргоог удирдаж, хувилбарын хяналтад байгаа
> тохиргооны файлуудаасаа компьютерийнхээ шинэ хуулбарыг амархан босгож болно.

Програм хангамжийн мөнхийн зөрчил: шинэ хувилбарууд санаатай ч бай, санамсаргүй ч
бай кодыг эвддэг, харин хуучин хувилбаруудад цаг хугацааны явцад аюулгүй байдлын
цоорхой илэрдэг. Үүнийг тасралтгүй интеграцаар програмаа шинэ хувилбарууд дээр
автоматаар шалгах ([Кодын чанар](/2026/code-quality/) лекцийг үзээрэй), мөн
[Dependabot](https://github.com/dependabot) шиг хэрэгслээр хамаарлын шинэ хувилбар
гармагц мэдэх замаар шийдэж болно.

CI-ийн тестүүдтэй байсан ч хувилбар ахиулахад хөгжүүлэлтийн болон бодит орчны
ялгаанаас болж асуудал гарсаар байдаг. Ийм үед хамгийн сайн арга бол шинэчлэлийг
буцааж, өмнөх тогтвортой хувилбарыг дахин байршуулах _буцаах төлөвлөгөөтэй_
(rollback plan) байх.

# Виртуал машин ба контейнер {#vms--containers}

Илүү нарийн хамаарал хэрэглэж эхлэхэд кодын тань хамаарал багц менежерийн даах
хэмжээнээс давж магадгүй. Нийтлэг шалтгаан нь системийн тусгай сан эсвэл тоног
төхөөрөмжийн драйвертай ажиллах хэрэгцээ. Жишээ нь шинжлэх ухааны тооцоолол, AI-ийн
салбарт програмууд GPU-г ашиглахын тулд тусгай сан, драйвер шаарддаг. Системийн
түвшний олон хамаарал (GPU драйвер, хөрвүүлэгчийн тодорхой хувилбар, OpenSSL шиг
дундын сан) одоо ч бүх системд суулгахыг шаарддаг.

Уламжлалт байдлаар ийм өргөн хүрээний хамаарлын асуудлыг виртуал машинаар (VM)
шийддэг байсан. Виртуал машин компьютерийг бүхэлд нь дуурайж, өөрийн үйлдлийн
системтэй бүрэн тусгаарлагдсан орчин бүрдүүлдэг. Харин орчин үеийн арга бол
_контейнер_ (container): програмыг хамаарал, сан, файлын системтэй нь хамт багцалдаг
ч компьютерийг бүхэлд нь дуурайлгүй хостын үйлдлийн системийн цөмийг хуваалцдаг.
Цөмөө хуваалцдаг учраас контейнер виртуал машинаас хамаагүй хөнгөн: хурдан асдаг,
нөөц бага иддэг.

Хамгийн алдартай контейнерийн платформ бол [Docker](https://www.docker.com/).
Docker контейнер угсрах, түгээх, ажиллуулах нэгдсэн стандартыг бий болгосон.
Цаанаа Docker контейнер ажиллуулахдаа containerd-ийг ашигладаг; Kubernetes зэрэг
бусад хэрэгсэл ч мөн үүнийг хэрэглэдэг салбарын стандарт.

Контейнер ажиллуулах амархан. Жишээ нь контейнер дотор Python-ы интерпретатор
ажиллуулахдаа `docker run` хэрэглэнэ (`-it` флаг контейнерийг терминалтай тань
интерактив байдлаар холбоно; терминалаас гарахад контейнер зогсоно).

```console
$ docker run -it python:3.12 python
Python 3.12.7 (main, Nov  5 2024, 02:53:25) [GCC 12.2.0] on linux
>>> print("Hello from inside a container!")
Hello from inside a container!
```

Бодит байдал дээр програм тань системийн хэмжээний файлын бүтцээс хамаарч болно.
Үүнийг шийдэхийн тулд програм ажиллахад хэрэгтэй файлын системийг бүхэлд нь
бүтээгдэхүүн болгож авч явдаг контейнерийн image ашигладаг.
Эдгээр image-ийг кодоор тодорхойлж үүсгэдэг. Docker-т Dockerfile-ийн синтаксаар
image дотор байх хамаарал, системийн сан, тохиргоогоо зааж өгнө:

```dockerfile
FROM python:3.12
RUN apt-get update
RUN apt-get install -y gcc
RUN apt-get install -y libpq-dev
RUN pip install numpy
RUN pip install pandas
COPY . /app
WORKDIR /app
RUN pip install .
```

Чухал ялгаа: Docker-ийн **image** бол багцалсан бүтээгдэхүүн (загвар гэж бодож
болно), харин **контейнер** бол тэр image-ээс ажиллаж буй бодит хуулбар. Нэг
image-ээс олон контейнер зэрэг ажиллуулж болно. Image давхаргуудаас (layer)
бүрддэг. Dockerfile доторх заавар бүр (`FROM`, `RUN`, `COPY` г.м.) шинэ давхарга
үүсгэнэ. Docker давхаргуудыг кэшэлдэг тул Dockerfile-ийн нэг мөр өөрчлөгдвөл
зөвхөн тэр мөр болон түүнээс хойших давхаргууд дахин угсрагдана.

Дээрх Dockerfile хэд хэдэн сул талтай: жижиг (slim) хувилбарын оронд бүтэн Python
image ашигласан, тусдаа `RUN` командуудаар илүүц давхаргууд үүсгэсэн, хувилбаруудыг
тогтоогоогүй, багц менежерийн кэшийг цэвэрлээгүй тул хэрэггүй файлууд image
дотор үлдсэн. Мөн контейнерийг root хэрэглэгчээр ажиллуулах, нууц мэдээллээ
санамсаргүй image-ийн давхаргад үлдээх нь түгээмэл алдаа.

Сайжруулсан хувилбар:

```dockerfile
FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
RUN apt-get update && \
    apt-get install -y --no-install-recommends gcc libpq-dev && \
    rm -rf /var/lib/apt/lists/*
COPY pyproject.toml uv.lock ./
RUN uv pip install --system -r uv.lock
COPY . /app
```

Энд `uv`-ийг эх кодоос угсрахын оронд `ghcr.io/astral-sh/uv:latest` image-ээс бэлэн
бинари файлыг нь хуулж авч байна. Үүнийг _угсрагч загвар_ (builder pattern) гэдэг.
Ингэснээр кодоо угсрахад хэрэгтэй бүх хэрэгслийг эцсийн image дотор үлдээх
шаардлагагүй; програм ажиллахад хэрэгтэй бинари л үлдэнэ.

Docker хэрэглэхэд анхаарах хэдэн хязгаарлалт бий. Нэгдүгээрт, контейнерийн image
ихэвчлэн тодорхой платформд зориулагдсан байдаг --- `linux/amd64`-д угсарсан image
`linux/arm64` (Apple Silicon Mac) дээр дуурайлгах (emulation) хэрэгсэлгүйгээр
ажиллахгүй, дуурайлгавал их удаан. Хоёрдугаарт, контейнерт Linux-ийн цөм хэрэгтэй
тул macOS, Windows дээр Docker цаанаа хөнгөн Linux виртуал машин ажиллуулдаг нь
нэмэлт ачаалал үүсгэнэ. Гуравдугаарт, Docker-ийн тусгаарлалт виртуал машинаас сул
--- контейнерүүд хостын цөмийг хуваалцдаг тул олон хэрэглэгчтэй (multi-tenant)
орчинд аюулгүй байдлын эрсдэл үүсч болно.

> Өнөө үед олон төсөл [nix flakes](https://serokell.io/blog/practical-nix-flakes)-ээр
> дамжуулан nix ашиглаж, бүр "системийн хэмжээний" сан, програмуудаа төсөл бүрээр
> удирдаж байна.

# Тохиргоо {#configuration}

Програм хангамж угаасаа тохируулагддаг. [Командын мөрийн
орчин](/2026/command-line-environment/) лекцээр програмууд флаг, орчны хувьсагч,
тохиргооны файлаар (dotfiles) тохиргоо авдгийг үзсэн. Нарийн програмуудад ч энэ
хамаатай, тохиргоог томоохон хэмжээнд удирдах тогтсон арга барилууд бий. Тохиргоог
кодонд шууд бичиж болохгүй, ажиллах үед нь (runtime) өгөх ёстой. Хамгийн түгээмэл
хоёр арга бол орчны хувьсагч ба тохиргооны файл.

Орчны хувьсагчаар тохиргоо авдаг програмын жишээ:

```python
import os

DATABASE_URL = os.environ.get("DATABASE_URL", "sqlite:///local.db")
DEBUG = os.environ.get("DEBUG", "false").lower() == "true"
API_KEY = os.environ["API_KEY"]  # Required - will raise if not set
```

Мөн програмыг тохиргооны файлаар тохируулж болно (жишээ нь `yaml.load`-оор
тохиргоогоо уншдаг Python програм), `config.yaml`:

```yaml
database:
  url: "postgresql://localhost/myapp"
  pool_size: 5
server:
  host: "0.0.0.0"
  port: 8080
  debug: false
```

Тохиргооны алтан дүрэм: нэг код огт өөрчлөгдөхгүйгээр, зөвхөн тохиргоог солиод өөр
өөр орчинд (хөгжүүлэлт, туршилт, бодит) ажиллах ёстой.

Тохиргоонд ихэвчлэн API түлхүүр гэх мэт эмзэг мэдээлэл ордог. Эдгээр нууцыг
(secrets) санамсаргүй задруулахгүйн тулд их болгоомжтой хандаарай, хувилбарын
хяналтад хэзээ ч бүү оруулаарай.

# Үйлчилгээ ба зохицуулалт {#services--orchestration}

Орчин үеийн програм ганцаараа ажиллах нь ховор. Жишээ нь вэб програмд өгөгдөл
хадгалах өгөгдлийн сан, хурдыг сайжруулах кэш, арын ажлуудыг ажиллуулах дараалал
(message queue) гэх мэт туслах үйлчилгээ хэрэгтэй болдог. Бүгдийг нэг цул (monolith)
програмд багтаахын оронд орчин үеийн архитектур тэдгээрийг тус тусдаа хөгжүүлж,
байршуулж, өргөтгөж болох үйлчилгээнүүдэд хуваахыг илүүд үздэг.

Жишээ нь програмдаа кэш хэрэгтэй гэж шийдвэл өөрсдөө шинээр бичихийн оронд
[Redis](https://redis.io/), [Memcached](https://memcached.org/) шиг туршигдсан бэлэн
шийдлийг ашиглаж болно. Redis-ийг програмынхаа контейнер дотор суулгаж болох ч
тэгвэл програм болон Redis-ийн бүх хамаарлыг нийцүүлэх хэрэгтэй болно, энэ нь
хэцүү, бүр боломжгүй байж магадгүй. Үүний оронд бүрэлдэхүүн хэсэг бүрийг тусдаа
контейнерт байршуулж болно. Үүнийг _микросервис архитектур_ гэдэг: хэсэг бүр бие
даасан үйлчилгээ болж ажиллаад, сүлжээгээр (ихэвчлэн HTTP API-аар) хоорондоо
харилцана.

[Docker Compose](https://docs.docker.com/compose/) бол олон контейнертэй програмыг
тодорхойлж, ажиллуулах хэрэгсэл. Контейнер бүрийг тусад нь удирдахын оронд бүх
үйлчилгээгээ нэг YAML файлд зарлаад, хамтад нь удирдана. Одоо манай програм
хэд хэдэн контейнертэй боллоо:

```yaml
# docker-compose.yml
services:
  web:
    build: .
    ports:
      - "8080:8080"
    environment:
      - REDIS_URL=redis://cache:6379
    depends_on:
      - cache

  cache:
    image: redis:7-alpine
    volumes:
      - redis_data:/data

volumes:
  redis_data:
```

`docker compose up` ажиллуулахад хоёр үйлчилгээ хамт асна. Вэб програм Redis рүү
`cache` гэдэг хостын нэрээр холбогдож чадна (Docker-ийн дотоод DNS үйлчилгээний
нэрийг автоматаар хаяг руу хөрвүүлдэг). Docker Compose нэг буюу хэд хэдэн
үйлчилгээг хэрхэн байршуулахыг тодорхойлж, тэднийг хамт ажиллуулах, сүлжээг
тохируулах, өгөгдөл хадгалах дундын эзлэхүүнийг (volume) удирдах ажлыг хариуцдаг.

Бодит орчинд байршуулахдаа docker compose үйлчилгээнүүдээ систем асахад автоматаар
эхэлж, алдаа гарвал өөрөө дахин асдаг байлгамаар байх. Нийтлэг нэг арга бол
docker compose-ийг systemd-ээр удирдах:

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My Application
Requires=docker.service
After=docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose down

[Install]
WantedBy=multi-user.target
```

Энэ systemd-ийн тохиргоо систем асахад (Docker бэлэн болсны дараа) програмыг тань
автоматаар эхлүүлнэ. Мөн `systemctl start myapp`, `systemctl stop myapp`,
`systemctl status myapp` гэх мэт стандарт командуудаар удирдаж болно.

Байршуулалтын шаардлага ахих тусам --- олон машинд тархаж өргөтгөх, үйлчилгээ
унахад автоматаар сэргээх, байнга ажиллаж байх (high availability) --- байгууллагууд
олон мянган контейнерийг зэрэг удирдаж чаддаг Kubernetes (k8s) шиг контейнер
зохицуулалтын платформ руу шилждэг. Гэхдээ Kubernetes сурахад хэцүү, ажиллуулж
арчлахад их зардалтай тул жижиг төсөлд хэтэрхий нүсэр.

Олон контейнертэй ийм тохиргоо ажиллах боломжтой байгаагийн нэг шалтгаан нь
орчин үеийн үйлчилгээнүүд стандарт API, ялангуяа HTTP REST API-аар хоорондоо
харилцдаг явдал. Жишээ нь програм OpenAI эсвэл Anthropic зэрэг LLM үйлчилгээ
үзүүлэгчтэй харьцах бүрдээ цаанаа тэдний сервер рүү HTTP хүсэлт илгээж, хариуг нь
задалдаг:

```console
$ curl https://api.anthropic.com/v1/messages \
    -H "x-api-key: $ANTHROPIC_API_KEY" \
    -H "content-type: application/json" \
    -H "anthropic-version: 2023-06-01" \
    -d '{"model": "claude-sonnet-4-20250514", "max_tokens": 256,
         "messages": [{"role": "user", "content": "Explain containers vs VMs in one sentence."}]}'
```

# Нийтлэх {#publishing}

Код тань зөв ажиллаж байгааг баталсны дараа бусад хүн татаж суулгаж болохоор
түгээмээр санагдаж магадгүй. Түгээх олон арга бий, хэрэглэж буй хэл, орчноос тань
шууд хамаарна.

Хамгийн энгийн арга бол бүтээгдэхүүнээ вэбэд тавиад, хүмүүст татаж аваад өөрсдөө
суулгуулах. Энэ арга одоо ч хэрэглэгдсээр байна, жишээ нь [Ubuntu-ийн багцын
архив](http://archive.ubuntu.com/ubuntu/pool/main/) үндсэндээ `.deb` файлуудын
жагсаалтыг вэбээр харуулдаг.

Өнөө үед эх код, бүтээгдэхүүнээ нийтлэх гол газар бол GitHub. Эх код ихэвчлэн
нээлттэй, харин GitHub Releases хувилбар бүрт бэлэн бинари болон бусад
бүтээгдэхүүнийг хавсаргаж нийтлэх боломж өгдөг.

Багц менежерүүд заримдаа GitHub-аас шууд, эх кодоос эсвэл бэлэн wheel-ээс суулгаж
чаддаг:

```console
# Install from source (will clone and build)
$ pip install git+https://github.com/psf/requests.git

# Install from a specific tag/branch
$ pip install git+https://github.com/psf/requests.git@v2.32.3

# Install a wheel directly from a GitHub release
$ pip install https://github.com/user/repo/releases/download/v1.0/package-1.0-py3-none-any.whl
```

Go шиг зарим хэл бүр төвлөрсөн бус түгээлттэй: төвлөрсөн багцын сангийн оронд Go
модулиуд эх кодын репоноосоо шууд түгээгддэг. `github.com/gorilla/mux` гэх мэт
модулийн зам код хаана байгааг заадаг бөгөөд `go get` тэндээс шууд татна. Гэхдээ
`pip`, `cargo`, `brew` зэрэг ихэнх багц менежер түгээх, суулгахыг хялбар болгохын
тулд бэлэн багцуудын төвлөрсөн жагсаалт (index) ашигладаг. Ийм команд ажиллуулбал:

```console
$ uv pip install requests --verbose --no-cache 2>&1 | grep -F '.whl'
DEBUG Selecting: requests==2.32.5 [compatible] (requests-2.32.5-py3-none-any.whl)
DEBUG No cache entry for: https://files.pythonhosted.org/packages/1e/db/4254e3eabe8020b458f1a747140d32277ec7a271daf1d235b70dc0b4e6e3/requests-2.32.5-py3-none-any.whl.metadata
DEBUG No cache entry for: https://files.pythonhosted.org/packages/1e/db/4254e3eabe8020b458f1a747140d32277ec7a271daf1d235b70dc0b4e6e3/requests-2.32.5-py3-none-any.whl
```

`requests`-ийн wheel хаанаас татагдаж байгааг харж болно. Файлын нэр дэх
`py3-none-any`-д анхаараарай --- энэ wheel ямар ч үйлдлийн систем, ямар ч архитектур
дээр, Python 3-ийн дурын хувилбартай ажиллана гэсэн үг. Харин хөрвүүлсэн код
агуулсан багцын wheel тодорхой платформд зориулагдсан байдаг:

```console
$ uv pip install numpy --verbose --no-cache 2>&1 | grep -F '.whl'
DEBUG Selecting: numpy==2.2.1 [compatible] (numpy-2.2.1-cp312-cp312-macosx_14_0_arm64.whl)
```

Энд `cp312-cp312-macosx_14_0_arm64` нь энэ wheel зөвхөн macOS 14+ дээрх, ARM64
архитектуртай компьютерийн CPython 3.12-д зориулагдсан гэдгийг заана. Өөр
платформ дээр `pip` өөр wheel татах эсвэл эх кодоос угсарна.

Эсрэгээрээ, өөрийн хийсэн багцыг бусад хүн олж суулгахын тулд эдгээр бүртгэлийн
аль нэгэнд нийтлэх хэрэгтэй. Python-д гол бүртгэл нь
[Python Package Index (PyPI)](https://pypi.org). Суулгахтай адил нийтлэх хэд хэдэн
арга бий. `uv publish` багцаа PyPI руу илгээх орчин үеийн интерфейс өгдөг:

```console
$ uv publish --publish-url https://test.pypi.org/legacy/
Publishing greeting-0.1.0.tar.gz
Publishing greeting-0.1.0-py3-none-any.whl
```

Энд бид жинхэнэ PyPI-г бохирдуулахгүйн тулд нийтлэх үйл явцаа турших зориулалттай
тусдаа бүртгэл [TestPyPI](https://test.pypi.org)-г ашиглаж байна. Илгээсний дараа
TestPyPI-аас ингэж суулгана:

```console
$ uv pip install --index-url https://test.pypi.org/simple/ greeting
```

Програм нийтлэхэд анхаарах чухал зүйл бол итгэл. Хэрэглэгчид татаж авсан багц нь
үнэхээр танаас ирсэн, замдаа өөрчлөгдөөгүй гэдгийг яаж мэдэх вэ? Багцын бүртгэлүүд
бүрэн бүтэн байдлыг шалгах хяналтын нийлбэр (checksum) ашигладаг, зарим экосистем
зохиогчийг криптографаар батлах гарын үсэг (package signing) дэмждэг.

Хэл бүр өөрийн багцын бүртгэлтэй: Rust-д [crates.io](https://crates.io),
JavaScript-д [npm](https://www.npmjs.com), Ruby-д [RubyGems](https://rubygems.org),
контейнерийн image-д [Docker Hub](https://hub.docker.com) гэх мэт. Хувийн эсвэл
дотоод багцуудад байгууллагууд өөрсдийн бүртгэлийг (жишээ нь хувийн PyPI сервер,
хувийн Docker бүртгэл) ажиллуулдаг, эсвэл cloud үйлчилгээ үзүүлэгчдийн бэлэн
шийдлийг ашигладаг.

Вэб үйлчилгээг интернэтэд гаргахад нэмэлт дэд бүтэц хэрэгтэй: домэйн нэр бүртгүүлэх,
домэйноо сервер рүүгээ заах DNS тохиргоо, HTTPS-ийг хариуцаж, урсгалыг чиглүүлэх nginx
шиг урвуу прокси (reverse proxy). Баримт бичиг, статик вэбсайт гэх мэт энгийн
тохиолдолд [GitHub Pages](https://pages.github.com/) репоноос шууд үнэгүй байршуулж
өгдөг.

# Дасгал ажил

1. Орчны хувьсагчдаа `printenv`-ээр файлд хадгалаад, venv үүсгэж идэвхжүүлээд,
   дахин орчны хувьсагчдаа өөр файлд хадгалж `diff before.txt after.txt`-ээр
   харьцуулаарай. Орчинд юу өөрчлөгдсөн бэ? Шелл яагаад venv доторх програмыг
   түрүүлж олж байна вэ? (Сэжүүр: идэвхжүүлэхийн өмнөх, дараах `$PATH`-ыг
   хараарай.) `which deactivate` ажиллуулаад deactivate bash функц юу хийдгийг
   бодоорой.
1. `pyproject.toml`-тэй Python багц үүсгээд виртуал орчинд суулгаарай. Lock файл
   үүсгээд агуулгыг нь харж үзээрэй.
1. Docker суулгаад Missing Semester-ийн сайтыг docker compose ашиглан өөрийн
   машин дээр угсарч ажиллуулаарай.
1. Энгийн Python програмд Dockerfile бичээрэй. Дараа нь програмаа Redis кэштэй
   хамт ажиллуулдаг `docker-compose.yml` бэлдээрэй.
1. Өөрийн Python багцаа TestPyPI-д нийтлээрэй (бусадтай хуваалцах үнэ цэнэтэй
   биш бол жинхэнэ PyPI-д бүү нийтлээрэй!). Дараа нь тэр багцтай Docker image
   үүсгээд `ghcr.io` руу илгээгээрэй.
1. [GitHub Pages](https://docs.github.com/en/pages/quickstart) ашиглан вэбсайт
   хийгээрэй. Нэмэлт: өөрийн домэйноо холбоорой.
