Програмчлалын алтан дүрэм: код таны бодсон шиг биш, таны бичсэн шиг ажилладаг.
Тэр хоёрын зөрүүг олох нь заримдаа хамгийн хэцүү ажил болдог. Энэ лекцээр алдаатай
кодыг дебаг хийх, мөн удаан эсвэл нөөц их иддэг кодыг профайлинг хийж ойлгох
аргуудыг үзнэ.

# Дебаг хийх

## Print ашиглан дебаг хийх ба лог

> "Алдаа засах хамгийн үр дүнтэй хэрэгсэл бол анхааралтай бодох, зөв газарт нь
> тавьсан print хоёр хэвээрээ." — Brian Kernighan, _Unix for Beginners_.

Дебаг хийх хамгийн эхний, хамгийн энгийн арга бол асуудалтай хэсгийн ойролцоо
print нэмээд, юу болоод байгааг ойлгох хүртлээ дахин дахин ажиллуулж харах.

Дараагийн шат нь хаа сайгүй санамсаргүй print тавихын оронд лог ашиглах. Лог
гэдэг нь үндсэндээ "сайн зохион байгуулалттай print" бөгөөд ихэвчлэн логийн
фреймворкийн дараах боломжууд дээр тулгуурладаг:

- логийг (эсвэл тодорхой хэсгийг нь) өөр газар (файл гэх мэт) рүү чиглүүлэх;
- ноцтой байдлын түвшин (INFO, DEBUG, WARN, ERROR гэх мэт) тавьж, гаралтыг түүгээр
  шүүх;
- логтой холбоотой өгөгдлийг бүтэцтэй лог (structured logging) хэлбэрээр хадгалах,
  ингэвэл дараа нь задлан шинжлэхэд амар.

Код бичиж байхдаа зөв газарт нь лог тавьчихвал дараа дебаг хийхэд хэрэгтэй өгөгдөл
аль хэдийн бэлэн байна. Print ашиглан асуудлаа олоод зассаны дараа бүгдийг нь устгахын
оронд хэрэгтэйг нь лог болгож үлдээвэл ирээдүйд ижил асуудал гарахад кодоо дахин
өөрчлөхгүйгээр учрыг нь олж чадна.

> **Бусдын програмын лог**: Олон програм ажиллахдаа илүү дэлгэрэнгүй мэдээлэл
> хэвлэх `-v` эсвэл `--verbose` флаг дэмждэг. Команд яагаад амжилтгүй болсныг
> олоход их хэрэг болно. Зарим нь флагийг давтаж өгвөл (`-vvv`) бүр дэлгэрэнгүй
> болдог. Үйлчилгээний (өгөгдлийн сан, вэб сервер гэх мэт) асуудлыг хайхдаа логийг
> нь шалгаарай --- Linux дээр ихэвчлэн `/var/log/`-д байдаг. Systemd үйлчилгээний
> логийг `journalctl -u <service>`-ээр харна. Бусдын сангуудын хувьд орчны хувьсагч
> эсвэл тохиргоогоор дебаг лог асаах боломж байгаа эсэхийг шалгаарай.

## Дебаггер

Print ашиглан дебаг хийх нь юуг хэвлэхээ мэдэж байгаа, кодоо амархан өөрчлөөд дахин
ажиллуулж болох үед тохиромжтой. Харин ямар мэдээлэл хэрэгтэйгээ мэдэхгүй, алдаа
нь зөвхөн дахин гаргахад хэцүү нөхцөлд гардаг, эсвэл програмаа өөрчлөөд дахин
эхлүүлэх нь өндөр өртөгтэй (удаан асдаг, төлөвийг нь дахин бүрдүүлэхэд төвөгтэй
гэх мэт) үед дебаггер их хэрэгтэй.

Дебаггер бол өөр програмын ажиллагааг ажиллаж байх зуур нь хянадаг
програм. Жишээ нь:

- Тодорхой мөрөнд хүрэхэд програмыг зогсоох (breakpoint).
- Кодыг нэг нэг заавраар алхуулж ажиллуулах.
- Програм унасны дараа хувьсагчдын утгыг шалгах.
- Тодорхой нөхцөл биелэхэд зогсоох (conditional breakpoint).
- Бас олон ахисан түвшний боломж.

Ихэнх програмчлалын хэл ямар нэг дебаггертэй эсвэл түүнийг дэмждэг. Хамгийн уян
хатан нь ямар ч бинари програмыг дебаг хийж чаддаг [`gdb`](https://www.gnu.org/software/gdb/)
(GNU Дебаггер), [`lldb`](https://lldb.llvm.org/) (LLVM Дебаггер) зэрэг **ерөнхий
зориулалтын дебаггер**-ууд. Мөн олон хэл өөрийн ажиллах орчинтой (runtime) илүү нягт холбогддог
**хэлний тусгай дебаггер**-тэй (Python-ы pdb, Java-гийн jdb гэх мэт).

`gdb` бол C, C++, Rust болон бусад хөрвүүлэгддэг (compiled) хэлний де-факто
стандарт дебаггер. Бараг ямар ч процессыг хянаж, машины одоогийн төлөвийг
харуулна: регистрүүд, стек, програмын тоолуур (program counter) гэх мэт.

Хэрэгтэй хэдэн GDB команд:

- `run` - Програмыг эхлүүлнэ
- `b {function}` эсвэл `b {file}:{line}` - Breakpoint тавина
- `c` - Үргэлжлүүлнэ
- `step` / `next` / `finish` - Функц руу орох / дээгүүр нь алхах / функцээс гарах
- `p {variable}` - Хувьсагчийн утгыг хэвлэнэ
- `bt` - Дуудлагын стекийг (backtrace) харуулна
- `watch {expression}` - Утга нь өөрчлөгдөхөд зогсооно (watchpoint)

> Командын мөрийн хажууд эх кодыг харахын тулд GDB-ийн TUI горимыг
> (`gdb -tui`, эсвэл GDB дотор `Ctrl-x a`) туршаад үзээрэй.

### Бичиж аваад дахин тоглуулж дебаг хийх (record-replay)

Хамгийн ядаргаатай алдаануудын нэг бол _Heisenbug_ буюу ажиглах гэхээр алга болдог
эсвэл өөрөөр гардаг алдаа. Уралдааны нөхцөл (race condition), цаг хугацаанаас
хамаарсан алдаа, зөвхөн системийн тодорхой нөхцөлд гардаг алдаа үүнд орно. Дахин
ажиллуулах бүрд үр дүн өөр гардаг тул уламжлалт дебаг ихэвчлэн үр дүнгүй (жишээ
нь print нэмэхэд код хангалттай удааширч, уралдааны нөхцөл гарахаа больж магадгүй).

**Record-replay debugging** үүнийг шийднэ: програмын ажиллагааг бичиж аваад, хүссэн
удаагаа яг адилхан, тодорхой (deterministic) байдлаар дахин тоглуулна. Бүр асуудал
хаана эхэлснийг олохын тулд ажиллагааг *ухрааж* ч болно.

[rr](https://rr-project.org/) бол програмын ажиллагааг бичиж аваад, бүрэн дебаг
хийх боломжтойгоор дахин тоглуулдаг Linux-ийн хүчтэй хэрэгсэл. GDB-тэй хамт
ажилладаг тул интерфейс нь танд аль хэдийн танил.

Үндсэн хэрэглээ:

```bash
# Record a program execution
rr record ./my_program

# Replay the recording (opens GDB)
rr replay
```

Ид шид нь дахин тоглуулах үед гардаг. Ажиллагаа тодорхой учраас **ухраах дебаг**
(reverse debugging) командууд ашиглаж болно:

- `reverse-continue` (`rc`) - Өмнөх breakpoint хүртэл ухрааж ажиллуулна
- `reverse-step` (`rs`) - Нэг мөр ухарна
- `reverse-next` (`rn`) - Функцийн дуудлагыг алгасаж ухарна
- `reverse-finish` - Одоогийн функцийг дуудсан газар хүртэл ухарна

Энэ дебаг хийхэд жинхэнэ хүч өгдөг. Програм унахад алдаа хаана гарсныг тааж
breakpoint тавихын оронд:

1. Унах цэг хүртэл ажиллуулна
2. Эвдэрсэн төлөвийг шалгана
3. Эвдэрсэн хувьсагч дээр watchpoint тавина
4. `reverse-continue` хийж тэр хувьсагч яг хаана эвдэрснийг олно

**rr-ийг хэзээ хэрэглэх вэ:**
- Хааяа амжилтгүй болдог тогтворгүй тестүүд
- Уралдааны нөхцөл болон олон тредтэй кодын алдаа
- Дахин гаргахад хэцүү уналтууд
- "Цагийг ухраамаар" санагдсан ямар ч алдаа

> Тэмдэглэл: rr зөвхөн Linux дээр ажиллана, мөн тоног төхөөрөмжийн гүйцэтгэлийн
> тоолуур (hardware performance counter) шаарддаг. Эдгээр тоолуурыг нээж өгдөггүй
> виртуал машин дээр (жишээ нь ихэнх AWS EC2 instance) ажиллахгүй, GPU хандалтыг ч
> дэмждэггүй. macOS дээр [Warpspeed](https://warpspeed.dev/)-ийг сонирхоорой.

> **rr ба зэрэгцээ ажиллагаа**: rr ажиллагааг тодорхой байдлаар бичихийн тулд
> тредүүдийг нэг нэгээр нь ээлжлүүлж ажиллуулдаг. Тиймээс зарим уралдааны нөхцөл
> rr дор гарахгүй байж магадгүй. Гэхдээ уралдааны нөхцөлийг дебаг хийхэд rr
> хэрэгтэй хэвээр: алдаатай ажиллагааг нэг удаа бичиж авбал түүнийг найдвартай дахин
> тоглуулж болно. Ховор алдааг барихын тулд хэд хэдэн удаа бичих хэрэг гарч
> магадгүй. Зэрэгцээ ажиллагаатай холбоогүй алдаанд rr бол хамгийн шилдэг нь:
> ажиллагааг яг таг дахин гаргаж, ухраах командуудаар санах ойн эвдрэлийг мөшгиж
> болно.

## Системийн дуудлагыг хянах

Заримдаа програм тань үйлдлийн системтэй хэрхэн харилцаж байгааг ойлгох хэрэгтэй
болдог. Програмууд цөмөөс (kernel) үйлчилгээ авахын тулд [системийн дуудлага](https://en.wikipedia.org/wiki/System_call)
(system call) хийдэг --- файл нээх, санах ой авах, процесс эхлүүлэх гэх мэт.
Эдгээр дуудлагыг хянаж үзэхэд програм яагаад гацаад байгаа, ямар файл руу хандах
гээд байгаа, хаана хүлээж цаг алдаж байгаа нь харагдаж болно.

### strace (Linux) ба dtruss (macOS)

[`strace`](https://www.man7.org/linux/man-pages/man1/strace.1.html) програмын хийж
буй системийн дуудлага бүрийг харуулна:

```bash
# Trace all system calls
strace ./my_program

# Trace only file-related calls
strace -e trace=file ./my_program

# Follow child processes (important for programs that start other programs)
strace -f ./my_program

# Trace a running process
strace -p <PID>

# Show timing information
strace -T ./my_program
```

> macOS, BSD дээр ижил зорилгоор `dtrace` дээр суурилсан [`dtruss`](https://www.manpagez.com/man/1/dtruss/)-ийг хэрэглэнэ.

> `strace`-ийг илүү гүнзгий сурмаар байвал Julia Evans-ийн гоё [strace zine](https://jvns.ca/strace-zine-unfolded.pdf)-ийг уншаарай.

### bpftrace ба eBPF

[eBPF](https://ebpf.io/) (extended Berkeley Packet Filter) бол Linux-ийн цөм дотор
тусгаарлагдсан (sandboxed) програм ажиллуулдаг хүчтэй технологи.
[`bpftrace`](https://github.com/iovisor/bpftrace) нь eBPF програм бичих өндөр
түвшний синтакс өгдөг. Эдгээр нь цөм дотор ажилладаг тул нэмэлт ачаалал (overhead)
бага. Системийн дуудлага тоолох, хугацаа хэмжих, аргумент шалгахад хэрэглэгддэг.

```bash
# Trace file opens system-wide (prints immediately)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'

# Count system calls by name (prints summary on Ctrl-C)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }'
```

Мөн [`bcc`](https://github.com/iovisor/bcc)-ээр eBPF програмыг C хэл дээр шууд бичиж
болно. Үүнд дискний үйлдлийн хоцролтыг хэмждэг `biosnoop`, файл нээлт бүрийг
хэвлэдэг `opensnoop` гэх мэт [олон бэлэн хэрэгсэл](https://www.brendangregg.com/blog/2015-09-22/bcc-linux-4.3-tracing.html)
бий.

`strace` хурдан эхлүүлэхэд амар, харин `bpftrace` нэмэлт ачаалал бага байх,
цөмийн функцуудыг хянах, нэгтгэсэн статистик гаргах хэрэгтэй үед илүү тохиромжтой.
`bpftrace` `root` эрх шаарддаг, нэг процесс биш бүх системийг хянадаг.
Тодорхой програмыг хянахын тулд командын нэр эсвэл PID-ээр шүүж болно:

```bash
# Filter by command name (prints summary on Ctrl-C)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /comm == "bash"/ { @[probe] = count(); }'

# Trace a specific command from startup using -c (cpid = child PID)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /pid == cpid/ { @[probe] = count(); }' -c 'ls -la'
```

`-c` флаг заасан командыг ажиллуулаад `cpid`-д түүний PID-ийг онооно. Ингэвэл
програмыг эхэлсэн мөчөөс нь хянахад амар. Програм дуусахад bpftrace нэгтгэсэн
үр дүнгээ хэвлэнэ.

### Сүлжээний асуудал хайх

Сүлжээний асуудалд [`tcpdump`](https://www.man7.org/linux/man-pages/man1/tcpdump.1.html),
[Wireshark](https://www.wireshark.org/) хоёроор сүлжээний пакетуудыг барьж аваад
задлан шинжилж болно:

```bash
# Capture packets on port 80
sudo tcpdump -i any port 80

# Capture and save to file for Wireshark analysis
sudo tcpdump -i any -w capture.pcap
```

HTTPS урсгал шифрлэгдсэн тул tcpdump-аар харахад нэг их юм олдохгүй.
[mitmproxy](https://mitmproxy.org/) шиг хэрэгслийг дундын прокси болгон хэрэглэж
шифрлэгдсэн урсгалыг харж болно. Вэб програмын хувьд хөтчийн хөгжүүлэгчийн
хэрэгсэл (Developer Tools-ийн Network таб) HTTPS хүсэлтийг шалгах хамгийн амар
арга: шифр нь тайлагдсан хүсэлт, хариу, header, хугацааг бүгдийг харуулна.

## Санах ойн алдаа хайх

Санах ойн алдаа --- буфер халих (buffer overflow), чөлөөлсний дараа ашиглах
(use-after-free), санах ой алдагдах (memory leak) --- бол хамгийн аюултай, дебаг
хийхэд хамгийн хэцүү алдаануудын нэг. Ихэвчлэн шууд унадаггүй, харин санах ойг
эвдээд дараа нь огт өөр газар асуудал үүсгэдэг.

### Sanitizer

Санах ойн алдаа олох нэг арга бол **sanitizer** ашиглах: програмыг ажиллаж байх
зуур нь алдааг илрүүлэх шалгалтуудыг хөрвүүлэгч (compiler) кодонд шигтгэж өгдөг
боломж. Жишээ нь өргөн хэрэглэгддэг **AddressSanitizer (ASan)** дараах алдааг олно:

- Буфер халих (стек, heap, глобал санах ойд)
- Чөлөөлсний дараа ашиглах (use-after-free)
- Функцээс буцсаны дараа ашиглах (use-after-return)
- Санах ой алдагдах

```bash
# Compile with AddressSanitizer
gcc -fsanitize=address -g program.c -o program
./program
```

Бусад хэрэгтэй sanitizer-ууд:

- **ThreadSanitizer (TSan)**: Олон тредтэй кодын өгөгдлийн уралдааныг (data race)
  илрүүлнэ (`-fsanitize=thread`)
- **MemorySanitizer (MSan)**: Утга оноогоогүй санах ой уншихыг илрүүлнэ
  (`-fsanitize=memory`)
- **UndefinedBehaviorSanitizer (UBSan)**: Бүхэл тооны халилт гэх мэт тодорхойгүй
  үйлдлийг (undefined behavior) илрүүлнэ (`-fsanitize=undefined`)

Sanitizer кодоо дахин хөрвүүлэхийг шаарддаг ч CI болон өдөр тутмын хөгжүүлэлтэд
хэрэглэхэд хангалттай хурдан.

### Valgrind: дахин хөрвүүлж чадахгүй үед

[Valgrind](https://valgrind.org/) санах ойн алдааг олохын тулд програмыг тань
виртуал машин маягийн орчинд ажиллуулдаг. Sanitizer-аас удаан ч дахин хөрвүүлэх
шаардлагагүй:

```bash
valgrind --leak-check=full ./my_program
```

Valgrind-ийг хэзээ хэрэглэх вэ:

- Эх код байхгүй үед
- Дахин хөрвүүлж чадахгүй үед (бусдын сан гэх мэт)
- Sanitizer-т байдаггүй тусгай хэрэгсэл хэрэгтэй үед

Valgrind үнэндээ кодыг хянах маш хүчтэй орчин. Профайлинг хэсэгт дахин гарч
ирнэ.

## Дебаг хийхэд AI ашиглах

LLM-үүд дебаг хийхэд гайхалтай туслах болоод байна. Уламжлалт хэрэгслүүдийг нөхөх
хэд хэдэн ажилд их сайн.

**LLM юунд сайн бэ:**

- **Ойлгомжгүй алдааны мессежийг тайлбарлах**: Хөрвүүлэгчийн алдаа, ялангуяа C++
  template эсвэл Rust-ийн borrow checker-ийн мессеж их ойлгомжгүй байдаг. LLM
  тэднийг энгийн хэлээр тайлбарлаад засах арга санал болгоно.
- **Хэл, давхаргын зааг дээр туслах**: Олон хэл дамжсан асуудал (жишээ нь Python-оос
  дуудаж буй C сангийн алдаа) засаж байгаа бол LLM эдгээр давхаргын хооронд
  шилжихэд тусална. FFI-ийн зааг, build системийн асуудал, олон хэл холилдсон
  дебагт их сайн (жишээ нь "миний програм унаад байна, гэхдээ миний ашигладаг нэг
  сангийн алдаа гэж бодож байна" гэх мэт үед).
- **Шинж тэмдгээс шалтгаан руу хөтлөх**: "Програм зөв ажиллаж байгаа ч хүлээснээс
  10 дахин их санах ой иддэг" гэх мэт бүрхэг шинж тэмдэг дээр юуг шалгах талаар
  санаа өгнө.
- **Уналтын dump, stack trace задлах**: Stack trace-ээ хуулж тавиад юунаас болж
  унасныг асууж болно.

> **Дебаг тэмдэгтийн тухай (дебаг symbols)**: Утга учиртай stack trace авч, дебаг
> хийхийн тулд бинари файлаа (мөн хамаарлуудаа) дебаг тэмдэгттэй (`-g` флаг)
> хөрвүүлэх хэрэгтэй. Дебаг мэдээлэл ихэвчлэн DWARF форматтай. Мөн frame pointer-тэй
> (`-fno-omit-frame-pointer`) хөрвүүлбэл stack trace, ялангуяа профайлинг хэрэгслүүдийнх,
> илүү найдвартай болно. Эдгээргүй бол stack trace зөвхөн санах ойн хаяг харуулах
> эсвэл дутуу гарч магадгүй. Энэ Python, Java-аас илүү хөрвүүлэгддэг хэлүүдэд чухал.

**Анхаарах зүйлс:**
- LLM итгэмээр сонсогдох ч буруу тайлбар зохиож болно
- Алдааг засахын оронд зөвхөн шинж тэмдгийг нь дарах засвар санал болгож магадгүй
- Санал болгосон засварыг бодит дебаг хэрэгслээр заавал шалгаарай
- LLM кодоо өөрөө ойлгохыг орлохгүй, зөвхөн тусална гэдгийг санаарай

> Энэ нь Хөгжүүлэлтийн орчин лекцээр үзсэн [AI-аар код бичих ерөнхий боломжоос](/2026/development-environment/#ai-powered-development)
> тусдаа. Энд бид зөвхөн LLM-ийг дебаг хийхэд туслагч болгох тухай ярьж байна.

# Профайлинг

Код тань зөв ажиллаж байлаа ч процессор, санах ойг бүгдийг нь идээд байвал
хангалтгүй. Алгоритмын хичээл ихэвчлэн big *O* тэмдэглэгээ заадаг ч програмын
хамгийн их цаг иддэг хэсгийг (hot spot) яаж олохыг заадаггүй.
[Хэт эрт оновчлох нь бүх муугийн үндэс](https://wiki.c2.com/?PrematureOptimization)
тул профайлер болон хяналтын хэрэгслүүдийг сурах хэрэгтэй. Эдгээр нь програмын аль
хэсэг хамгийн их цаг, нөөц зарцуулж байгааг харуулдаг тул зөвхөн тэр хэсгийг оновчлоход
анхаарлаа хандуулж болно.

## Хугацаа хэмжих

Гүйцэтгэлийг хэмжих хамгийн энгийн арга бол хугацаа хэмжих. Ихэнхдээ кодын хоёр
цэгийн хооронд цагийг хэвлэхэд л хангалттай.

Гэхдээ ханын цагийн хугацаа (wall clock time) төөрөгдүүлж магадгүй, учир нь компьютер
тань зэрэг өөр процессууд ажиллуулж байгаа эсвэл сүлжээний хариу хүлээж байж болно.
`time` команд _Real_, _User_, _Sys_ гэсэн гурван хугацааг ялгаж харуулдаг:

- **Real** - Эхнээс нь дуустал өнгөрсөн бодит хугацаа, хүлээсэн хугацааг оруулаад
- **User** - Хэрэглэгчийн кодыг ажиллуулахад процессорын зарцуулсан хугацаа
- **Sys** - Цөмийн кодыг ажиллуулахад процессорын зарцуулсан хугацаа

```bash
$ time curl https://missing.csail.mit.edu &> /dev/null
real	0m0.272s
user	0m0.079s
sys	    0m0.028s
```

Энд хүсэлт нийт 300 орчим миллисекунд үргэлжилсэн ч процессорын хугацаа ердөө
107ms (user + sys). Үлдсэн хугацаа сүлжээг хүлээхэд өнгөрсөн.

## Нөөцийн хэрэглээг хянах

Заримдаа гүйцэтгэлийг шинжлэх эхний алхам бол програм бодитоор хэр их нөөц
хэрэглэж байгааг ойлгох. Нөөц хүрэлцэхгүй болоход програмууд ихэвчлэн удааширдаг.

- **Ерөнхий хяналт**: [`htop`](https://htop.dev/) бол ажиллаж буй процессуудын
  янз бүрийн статистикийг харуулдаг `top`-ийн сайжруулсан хувилбар. Хэрэгтэй
  товчнууд: `<F6>` процессуудыг эрэмбэлэх, `t` модон бүтцээр харуулах, `h`
  тредүүдийг харуулах/нуух. Бүр *илүү олон* зүйл хянадаг [`btop`](https://github.com/aristocratos/btop) ч бий.
- **Дискний I/O**: [`iotop`](https://www.man7.org/linux/man-pages/man8/iotop.8.html)
  дискний оролт/гаралтыг шууд харуулна.
- **Санах ойн хэрэглээ**: [`free`](https://www.man7.org/linux/man-pages/man1/free.1.html)
  нийт, сул, ашиглагдаж буй санах ойг харуулна.
- **Нээлттэй файлууд**: [`lsof`](https://www.man7.org/linux/man-pages/man8/lsof.8.html)
  процессуудын нээсэн файлуудыг жагсаана. Тодорхой файлыг аль процесс нээснийг
  шалгахад их хэрэгтэй.
- **Сүлжээний холболт**: [`ss`](https://www.man7.org/linux/man-pages/man8/ss.8.html)
  сүлжээний холболтуудыг харуулна. Хамгийн түгээмэл хэрэглээ нь аль процесс тодорхой
  портыг эзэлж байгааг олох: `ss -tlnp | grep :8080`.
- **Сүлжээний ачаалал**: [`nethogs`](https://github.com/raboof/nethogs),
  [`iftop`](https://pdw.ex-parrot.com/iftop/) процесс бүрийн сүлжээний хэрэглээг
  харуулдаг интерактив командын мөрийн хэрэгслүүд.

## Гүйцэтгэлийн өгөгдлийг дүрслэх

Хүн тооны хүснэгтээс илүү график дээрх зүй тогтлыг хурдан олж хардаг. Гүйцэтгэлийг
шинжлэхдээ өгөгдлөө зураг болгоход тоон дундаас харагдахгүй чиг хандлага, огцом
өсөлт, гажуудал ил гарч ирдэг.

**Өгөгдлөө зурахад бэлэн болго**: Дебаг хийхдээ print эсвэл лог нэмэх бол дараа нь
график болгоход амар форматаар бичээрэй. CSV хэлбэрийн энгийн цагийн тэмдэг, утга
(`1705012345,42.5`) урт өгүүлбэрээс хамаагүй амархан зурагдана. JSON бүтэцтэй
логийг ч бага хүчээр задалж зурж болно. Өөрөөр хэлбэл өгөгдлөө
[цэгцтэй (tidy)](https://vita.had.co.nz/papers/tidy-data.pdf) хэлбэрээр логлоорой.

**Gnuplot-оор хурдан зурах**: Командын мөрөөс хурдан график зурах бол
[`gnuplot`](http://www.gnuplot.info/) өгөгдлийн файлаас шууд график гаргана:

```bash
# Plot a simple CSV with timestamp,value
gnuplot -e "set datafile separator ','; plot 'latency.csv' using 1:2 with lines"
```

**Matplotlib, ggplot2-оор гүнзгий судлах**: Илүү нарийн шинжилгээнд Python-ы
[`matplotlib`](https://matplotlib.org/), R-ийн [`ggplot2`](https://ggplot2.tidyverse.org/)
өгөгдлийг интерактив байдлаар судлах боломжтой. Нэг удаагийн зурагнаас ялгаатай
нь эдгээрээр өгөгдлөө хурдан хувааж, таамаглалаа шалгаж болно. ggplot2-ийн facet
plot их хэрэгтэй --- нэг өгөгдлийг ангиллаар нь (жишээ нь хүсэлтийн хоцролтыг
endpoint эсвэл өдрийн цагаар) олон жижиг график болгон хувааж, нуугдмал зүй
тогтлыг ил гаргана.

**Хэрэглээний жишээ:**
- Хүсэлтийн хугацааг цаг хугацааны дагуу зурахад үе үе гардаг удаашрал (garbage
  collection, cron ажил, ачааллын хэлбэлзэл) харагддаг, дундаж тоо үүнийг нуудаг
- Өсөж буй өгөгдлийн бүтцэд элемент нэмэх хугацааг зурвал алгоритмын нарийн
  төвөгтэй байдлын асуудал ил гарна --- жишээ нь динамик массив (vector) хэмжээгээ
  хоёр дахин томруулах бүрд гардаг огцом өсөлтүүд графикаас тод харагдана
- Өгөгдлийг өөр өөр хэмжигдэхүүнээр (хүсэлтийн төрөл, хэрэглэгчийн бүлэг, сервер)
  салгаж зурвал "бүх системд гараад байгаа" асуудал үнэндээ зөвхөн нэг ангилалд
  хамаатай байх нь олддог

## CPU профайлер

Хүмүүс *профайлер* гэж ярихдаа ихэвчлэн *CPU профайлер*-ийг хэлдэг. Үндсэн хоёр төрөл бий:

- **Мөрддөг (tracing) профайлер** програмын хийсэн функцийн дуудлага бүрийг бүртгэнэ
- **Түүвэрлэдэг (sampling) профайлер** програмыг үе үе (ихэвчлэн миллисекунд тутам) шалгаж,
  тухайн үеийн стекийг тэмдэглэнэ

Түүвэрлэдэг профайлер нэмэлт ачаалал багатай тул практикт илүү өргөн хэрэглэгддэг.

### perf: түүвэрлэдэг профайлер

[`perf`](https://www.man7.org/linux/man-pages/man1/perf.1.html) бол Linux-ийн
стандарт профайлер. Дахин хөрвүүлэлгүйгээр ямар ч програмыг хэмжиж чадна:

`perf stat` цаг хаана зарцуулагдаж байгааг товч харуулна:

```bash
$ perf stat ./slow_program

 Performance counter stats for './slow_program':

         3,210.45 msec task-clock                #    0.998 CPUs utilized
               12      context-switches          #    3.738 /sec
                0      cpu-migrations            #    0.000 /sec
              156      page-faults               #   48.587 /sec
   12,345,678,901      cycles                    #    3.845 GHz
    9,876,543,210      instructions              #    0.80  insn per cycle
    1,234,567,890      branches                  #  384.532 M/sec
       12,345,678      branch-misses             #    1.00% of all branches
```

Бодит програмын профайлерийн гаралт асар их мэдээлэлтэй байдаг. Хүн зурагт илүү
сайн тул урт тоон жагсаалт унших нь хэцүү. [**Flame graph**](https://www.brendangregg.com/flamegraphs.html)
(дөлөн график) бол профайлингийн өгөгдлийг ойлгоход хамаагүй амар болгодог дүрслэл.

Flame graph Y тэнхлэгийн дагуу функцийн дуудлагын шатлалыг, X тэнхлэгийн дагуу
зарцуулсан хугацааг харуулна. Интерактив байдаг --- тодорхой хэсэг дээр дарж
томруулж болно.

[![FlameGraph](https://www.brendangregg.com/FlameGraphs/cpu-bash-flamegraph.svg)](https://www.brendangregg.com/FlameGraphs/cpu-bash-flamegraph.svg)

`perf`-ийн өгөгдлөөс flame graph гаргахдаа:

```bash
# Record profile
perf record -g ./my_program

# Generate flame graph (requires flamegraph scripts)
perf script | stackcollapse-perf.pl | flamegraph.pl > flamegraph.svg
```

> Хөтөч дээр интерактив байдлаар харахад [Speedscope](https://www.speedscope.app/),
> системийн түвшний гүнзгий шинжилгээнд [Perfetto](https://perfetto.dev/)-г
> хэрэглэж болно.

### Valgrind-ийн Callgrind: мөрддөг профайлер

[`callgrind`](https://valgrind.org/docs/manual/cl-manual.html) програмын дуудлагын
түүх болон ажилласан зааврын тоог бүртгэдэг профайлер. Түүвэрлэдэг профайлерээс
ялгаатай нь дуудлагын яг тоог гаргаж, аль функц аль функцийг дуудаж байгааг харуулна:

```bash
# Run with callgrind
valgrind --tool=callgrind ./my_program

# Analyze with callgrind_annotate (text) or kcachegrind (GUI)
callgrind_annotate callgrind.out.<pid>
kcachegrind callgrind.out.<pid>
```

Callgrind түүвэрлэдэг профайлерээс удаан ч нарийн тоо гаргадаг, хүсвэл кэшийн
ажиллагааг ч дуурайж (`--cache-sim=yes`) болно.

> Тодорхой хэл дээр ажиллаж байгаа бол илүү тусгай хэрэгслүүд бий. Жишээ нь
> Python-д [`cProfile`](https://docs.python.org/3/library/profile.html),
> [`py-spy`](https://github.com/benfred/py-spy), Go-д [`go tool pprof`](https://pkg.go.dev/cmd/pprof),
> Rust-д [`cargo-flamegraph`](https://github.com/flamegraph-rs/flamegraph) (үнэндээ
> ямар ч хөрвүүлэгддэг програм дээр ажиллана!).

## Санах ойн профайлер

Санах ойн профайлер програм санах ойгоо цаг хугацааны явцад хэрхэн хэрэглэж байгааг
ойлгож, санах ой алдагдахыг олоход тусалдаг.

### Valgrind-ийн Massif

[`massif`](https://valgrind.org/docs/manual/ms-manual.html) heap санах ойн
хэрэглээг хэмждэг:

```bash
valgrind --tool=massif ./my_program
ms_print massif.out.<pid>
```

Heap-ийн хэрэглээг цаг хугацааны дагуу харуулж, санах ой алдагдах болон хэт их
санах ой авч байгаа газрыг олоход тусална.

> Python-д [`memory-profiler`](https://pypi.org/project/memory-profiler/) мөр
> бүрийн санах ойн хэрэглээг харуулдаг.

# Дасгал ажил

## Debugging

1. **Эрэмбэлэх алгоритмын алдаа засах**: Доорх псевдо код merge sort-ийг
   хэрэгжүүлсэн ч алдаатай. Үүнийг дуртай хэл дээрээ бичээд дебаггер (gdb, lldb,
   pdb, эсвэл IDE-ийнхээ дебаггер) ашиглан алдааг олж засаарай.

   ```
   function merge_sort(arr):
       if length(arr) <= 1:
           return arr
       mid = length(arr) / 2
       left = merge_sort(arr[0..mid])
       right = merge_sort(arr[mid..end])
       return merge(left, right)

   function merge(left, right):
       result = []
       i = 0, j = 0
       while i < length(left) AND j < length(right):
           if left[i] <= right[j]:
               append result, left[i]
               i = i + 1
           else:
               append result, right[i]
               j = j + 1
       append remaining elements from left and right
       return result
   ```

   Тест: `merge_sort([3, 1, 4, 1, 5, 9, 2, 6])` нь `[1, 1, 2, 3, 4, 5, 6, 9]`
   буцаах ёстой. Breakpoint тавиад merge функцээр алхаж, буруу элемент хаана
   сонгогдож байгааг олоорой.

1. [`rr`](https://rr-project.org/)-ийг суулгаад ухраах дебаг ашиглан санах ой
   эвдэрч буй алдааг олоорой. Энэ програмыг `corruption.c` нэрээр хадгалаарай:

   ```c
   #include <stdio.h>

   typedef struct {
       int id;
       int scores[3];
   } Student;

   Student students[2];

   void init() {
       students[0].id = 1001;
       students[0].scores[0] = 85;
       students[0].scores[1] = 92;
       students[0].scores[2] = 78;

       students[1].id = 1002;
       students[1].scores[0] = 90;
       students[1].scores[1] = 88;
       students[1].scores[2] = 95;
   }

   void curve_scores(int student_idx, int curve) {
       for (int i = 0; i < 4; i++) {
           students[student_idx].scores[i] += curve;
       }
   }

   int main() {
       init();
       printf("=== Initial state ===\n");
       printf("Student 0: id=%d\n", students[0].id);
       printf("Student 1: id=%d\n", students[1].id);

       curve_scores(0, 5);

       printf("\n=== After curving ===\n");
       printf("Student 0: id=%d\n", students[0].id);
       printf("Student 1: id=%d\n", students[1].id);

       if (students[1].id != 1002) {
           printf("\nERROR: Student 1's ID was corrupted! Expected 1002, got %d\n",
                  students[1].id);
           return 1;
       }
       return 0;
   }
   ```

   `gcc -g corruption.c -o corruption`-оор хөрвүүлээд ажиллуулаарай. Student 1-ийн
   ID эвдэрч байна, гэтэл бид зөвхөн student 0-ийг өөрчилдөг функц дуудсан.
   `rr record ./corruption`, `rr replay`-ээр алдааг олоорой. `students[1].id`
   дээр watchpoint тавиад, эвдэрсний дараа `reverse-continue` хийж яг аль мөр
   түүнийг дарж бичсэнийг олоорой.

1. AddressSanitizer ашиглан санах ойн алдааг засаарай. Үүнийг `uaf.c` нэрээр хадгалаарай:

   ```c
   #include <stdlib.h>
   #include <string.h>
   #include <stdio.h>

   int main() {
       char *greeting = malloc(32);
       strcpy(greeting, "Hello, world!");
       printf("%s\n", greeting);

       free(greeting);

       greeting[0] = 'J';
       printf("%s\n", greeting);

       return 0;
   }
   ```

   Эхлээд sanitizer-гүй хөрвүүлж ажиллуулаарай: `gcc uaf.c -o uaf && ./uaf`.
   Хэвийн ажиллаж байгаа юм шиг харагдаж магадгүй. Одоо AddressSanitizer-тэй
   хөрвүүлээрэй: `gcc -fsanitize=address -g uaf.c -o uaf && ./uaf`. Алдааны
   тайланг уншаарай. ASan ямар алдаа олсон бэ? Заасан асуудлыг нь засаарай.

1. `strace` (Linux) эсвэл `dtruss` (macOS) ашиглан `ls -l`-ийн хийж буй системийн
   дуудлагуудыг хянаарай. Ямар дуудлагууд хийгдэж байна вэ? Арай төвөгтэй програм
   хянаад ямар файлууд нээж байгааг хараарай.

1. Ойлгомжгүй алдааны мессежийг тайлах гэж LLM ашиглаад үзээрэй. Хөрвүүлэгчийн
   алдааг (ялангуяа C++ template эсвэл Rust-ийн алдаа) хуулж тавиад тайлбар, засвар
   асуугаарай. `strace` эсвэл AddressSanitizer-ийн гаралтыг ч оруулж үзээрэй.

## Профайлинг

1. Өөрийн сонгосон програм дээр `perf stat` ажиллуулж гүйцэтгэлийн үндсэн
   статистикийг аваарай. Тоолуур бүр юуг илэрхийлж байна вэ?

1. `perf record`-оор профайлинг хийгээрэй. Үүнийг `slow.c` нэрээр хадгалаарай:

   ```c
   #include <math.h>
   #include <stdio.h>

   double slow_computation(int n) {
       double result = 0;
       for (int i = 0; i < n; i++) {
           for (int j = 0; j < 1000; j++) {
               result += sin(i * j) * cos(i + j);
           }
       }
       return result;
   }

   int main() {
       double r = 0;
       for (int i = 0; i < 100; i++) {
           r += slow_computation(1000);
       }
       printf("Result: %f\n", r);
       return 0;
   }
   ```

   Дебаг тэмдэгттэй хөрвүүлээрэй: `gcc -g -O2 slow.c -o slow -lm`.
   `perf record -g ./slow` ажиллуулаад, дараа нь `perf report`-оор цаг хаана
   зарцуулагдаж байгааг хараарай. Flamegraph скриптүүдээр flame graph гаргаж
   үзээрэй.

1. `hyperfine` ашиглан нэг ажлыг хийдэг хоёр өөр хэрэгжүүлэлтийг харьцуулаарай
   (жишээ нь `find` ба `fd`, `grep` ба `ripgrep`, эсвэл өөрийн кодын хоёр хувилбар).

1. Нөөц их иддэг програм ажиллаж байх үед `htop`-оор хянаарай. Процессын ашиглаж
   болох процессорын цөмүүдийг `taskset`-ээр хязгаарлаж үзээрэй:
   `taskset --cpu-list 0,2 stress -c 3`. `stress` яагаад гурван цөм ашиглаж
   чадахгүй байна вэ?

1. Ашиглах гэсэн портыг тань өөр процесс аль хэдийн эзэлчихсэн байх нь түгээмэл
   асуудал. Үүнийг яаж олохыг сураарай: эхлээд `python -m http.server 4444`-ээр
   4444 порт дээр жижиг вэб сервер асаагаарай. Өөр терминал дээр
   `ss -tlnp | grep 4444` ажиллуулж тэр процессыг олоорой. `kill <PID>`-ээр
   зогсоогоорой.
