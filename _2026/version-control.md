Хувилбарын хяналтын систем (version control system, VCS) гэдэг нь эх код, эсвэл ер нь
файл, хавтасны өөрчлөлтийн түүхийг хадгалдаг хэрэгсэл. Өөрөөр хэлбэл төсөл тань
цаг хугацааны явцад яаж өөрчлөгдсөнийг харж, буцааж, бусадтай хамтарч ажиллаж
болно. Дотоод логикоороо VCS хавтасны төлөвийг цуврал _снапшот_ (snapshot) хэлбэрээр
хадгална: снапшот бүр тухайн мөчид төслийн дээд хавтас дотор байсан файл,
хавтсуудын бүрэн төлөвийг агуулна. Мөн снапшотыг хэн, хэзээ, ямар тайлбартай
үүсгэсэн гэх мэт мета өгөгдлийг хадгална.

Хувилбарын хяналт ганцаараа ажиллаж байсан ч хэрэгтэй. Өмнөх төлөвөө харах, "энэ
өөрчлөлтийг яагаад хийсэн билээ?" гэдгийг логоос олох, өөр өөр салаа дээр зэрэг
ажиллах боломжтой. Харин багаар ажиллах үед бусад хүн юу өөрчилснийг харах,
зөрчил шийдэх, нэг код дээр бие биендээ саад болохгүй ажиллах суурь нь болдог.

Орчин үеийн VCS ийм асуултуудад амархан, ихэнхдээ автоматаар хариулж өгнө:

- Энэ модулийг хэн бичсэн бэ?
- Энэ файлын яг энэ мөрийг хэзээ, хэн, юунд засварласан бэ?
- Сүүлийн 1000 өөрчлөлтийн дунд яг хэзээ, яагаад энэ unit тест ажиллахаа больсон бэ?

Өөр VCS-үүд ч бий, гэхдээ өнөөдөр **Git** бараг де-факто стандарт болсон. Git-ийн
нэр хүндийг энэ [XKCD комик](https://xkcd.com/1597/) их сайн илэрхийлдэг:

![xkcd 1597](https://imgs.xkcd.com/comics/git.png)

Git-ийн интерфейс дотоод бүтцээ нэлээд ил гаргадаг, өөрөөр хэлбэл "цоорхой
хийсвэрлэл" (leaky abstraction). Тиймээс Git-ийг шууд командуудаас нь, дээрээс нь
доошоо сурвал амархан төөрнө. Хүмүүс хэдэн команд цээжлээд шившлэг шиг хэрэглэдэг,
нэг юм эвдэрмэгц дээрх комик шиг бүгдийг устгаад шинээр clone хийдэг нь тийм ч ховор биш.

Git-ийн командын мөрийн интерфейс заримдаа эвгүй, гэхдээ цаад өгөгдлийн загвар нь
үнэхээр цэвэрхэн. Эвгүй интерфейсийг цээжилж болно, харин сайн загварыг ойлгочихвол
командууд цаанаа юу хийж байгааг тааж чаддаг болно. Тиймээс бид Git-ийг өгөгдлийн
загвараас нь эхэлж тайлбарлаад, дараа нь командууд руу орно.

# Git-ийн өгөгдлийн загвар

Git-ийн ухаалаг тал нь сайн бодож боловсруулсан өгөгдлийн загварт нь байгаа. Түүх
хадгалах, салаа дэмжих, хамтран ажиллах гээд хувилбарын хяналтын бүх сайн
боломжууд энэ загвараас үүдэлтэй.

## Снапшот {#snapshots}

Git дээд хавтас доторх файл, хавтсуудын түүхийг цуврал снапшот хэлбэрээр
загварчилдаг. Git-ийн нэр томьёогоор файлыг "blob" гэнэ: энэ нь зүгээр л хэдэн
байтын цуваа. Хавтсыг "tree" гэнэ: нэрсийг blob эсвэл өөр tree-тэй холбодог
(тиймээс хавтас дотор хавтас байж болно). Снапшот гэдэг нь хянагдаж буй хамгийн
дээд tree. Жишээ нь иймэрхүү tree байж болно:

```
<root> (tree)
|
+- foo (tree)
|  |
|  + bar.txt (blob, contents = "hello world")
|
+- baz.txt (blob, contents = "git is wonderful")
```

Хамгийн дээд tree хоёр зүйл агуулж байна: "foo" нэртэй tree (дотроо "bar.txt"
гэсэн ганц blob-той) болон "baz.txt" нэртэй blob.

## Түүхийг загварчлах: снапшотуудыг холбох нь

Хувилбарын хяналтын систем снапшотуудыг хооронд нь яаж холбох ёстой вэ? Хамгийн
энгийн загвар нь шугаман түүх: цаг хугацааны дарааллаар эрэмбэлсэн снапшотуудын
жагсаалт. Гэхдээ Git олон шалтгаанаар ийм энгийн загвар хэрэглэдэггүй.

Git-д түүх бол снапшотуудын чиглэлтэй, циклгүй граф (directed acyclic graph, DAG).
Математикийн хүнд үг шиг сонсогдож магадгүй, гэхдээ бүү ай. Энэ нь зүгээр л Git-ийн
снапшот бүр өөрөөсөө өмнөх снапшотууд буюу "эцэг" (parent)-үүдээ заадаг гэсэн
үг. Шугаман түүх шиг ганц эцэг биш, хэд хэдэн эцэгтэй байж болно, учир нь
зэрэгцэн хөгжсөн хоёр салааг нэгтгэхэд (merge) нэг снапшот хоёр эцэгтэй болдог.

Git эдгээр снапшотыг "коммит" гэж нэрлэдэг. Коммитуудын түүхийг ингэж
дүрсэлж болно:

```
o <-- o <-- o <-- o
            ^
             \
              --- o <-- o
```

Дээрх зурагт `o` бүр нэг коммит (снапшот). Сумнууд коммит бүрийн эцэг рүү
заана (энэ бол "өмнө нь ирсэн" гэсэн харьцаа, "дараа нь ирсэн" биш). Гурав дахь
коммитын дараа түүх хоёр тусдаа салаа болж хуваагдаж байна. Жишээ нь хоёр өөр
боломжийг бие биенээсээ хамааралгүй, зэрэг хөгжүүлж байгаа байж болно. Ирээдүйд
эдгээр салааг нэгтгэж (merge), хоёр боломжийг хоёуланг нь агуулсан шинэ
снапшот үүсгэж болно. Тэгвэл түүх ингэж харагдана (шинээр үүссэн нэгтгэлийн коммитыг
тодоор харуулав):

<pre class="highlight">
<code>
o <-- o <-- o <-- o <---- <strong>o</strong>
            ^            /
             \          v
              --- o <-- o
</code>
</pre>

Git-ийн коммитууд өөрчлөгддөггүй (immutable). Энэ нь алдааг засаж болохгүй гэсэн
үг биш; түүхийг "засах" үед цаанаа цоо шинэ коммитууд үүсдэг бөгөөд
лавлагаанууд (доор үзнэ) шинэ коммитууд руу заахаар шинэчлэгддэг.

## Өгөгдлийн загвар, псевдо кодоор

Git-ийн өгөгдлийн загварыг псевдо кодоор харах нь илүү ойлгомжтой байж магадгүй:

```
// a file is a bunch of bytes
type blob = array<byte>

// a directory contains named files and directories
type tree = map<string, tree | blob>

// a commit has parents, metadata, and the top-level tree
type commit = struct {
    parents: array<commit>
    author: string
    message: string
    snapshot: tree
}
```

Түүх хадгалах цэвэрхэн, энгийн загвар байгаа биз.

## Объект ба агуулгаар хаяглах

"Объект" гэдэг нь blob, tree, коммитын аль нэг:

```
type object = blob | tree | commit
```

Git-ийн өгөгдлийн санд бүх объект өөрийнхөө [SHA-1 хэшээр](https://en.wikipedia.org/wiki/SHA-1)
хаяглагддаг (content-addressed).

```
objects = map<string, object>

def store(object):
    id = sha1(object)
    objects[id] = object

def load(id):
    return objects[id]
```

Blob, tree, коммит бүгд ийм л объект. Бусад объектоо зааж байхдаа тэднийг дискэн
дээр өөр дотроо _агуулдаггүй_, харин хэшээр нь л заадаг.

Жишээ нь [дээрх](#snapshots) хавтасны бүтцийн tree (`git cat-file -p
698281bc680d1995c5f4caaf3359721a5a58d48d`-аар харвал) ийм байна:

```
100644 blob 4448adbf7ecd394f42ae135bbeed9676e894af85    baz.txt
040000 tree c68d233a33c5c06e0340e4c224f0afca87c8ce87    foo
```

Tree өөрийнхөө агуулга болох `baz.txt` (blob), `foo` (tree) хоёр руу заасан
заагчуудтай байна. `baz.txt`-ийн хэшээр хаяглагдсан агуулгыг
`git cat-file -p 4448adbf7ecd394f42ae135bbeed9676e894af85`-ээр харвал:

```
git is wonderful
```

## Лавлагаа {#references}

Одоо бүх снапшотыг SHA-1 хэшээр нь тодорхойлж болно. Гэхдээ энэ эвгүй, учир нь
хүн 40 тэмдэгттэй арван зургаатын тоог цээжлэхдээ муу.

Git-ийн шийдэл нь SHA-1 хэшүүдэд хүнд ойлгомжтой нэр өгөх: үүнийг "reference" (лавлагаа)
гэнэ. Лавлагаа бол коммит руу заасан заагч. Өөрчлөгддөггүй объектуудаас
ялгаатай нь лавлагаа өөрчлөгдөж болно (өөр коммит руу заахаар шинэчилж болно).
Жишээ нь `master` лавлагаа ихэвчлэн хөгжүүлэлтийн үндсэн салааны хамгийн
сүүлийн коммит руу заадаг.

```
references = map<string, string>

def update_reference(name, id):
    references[name] = id

def read_reference(name):
    return references[name]

def load_reference(name_or_id):
    if name_or_id in references:
        return load(references[name_or_id])
    else:
        return load(name_or_id)
```

Ингэснээр Git урт арван зургаатын тооны оронд "master" гэх мэт хүнд ойлгомжтой
нэрээр түүхийн тодорхой снапшотыг заадаг.

Нэг нарийн зүйл: түүхэн дээр "одоо хаана байна" гэдгийг мэдэх хэрэгтэй. Тэгж байж
шинэ снапшот авахдаа түүнийг юунтай холбохоо (коммитын `parents` талбарыг яаж
оноохоо) мэднэ. Git-д үүнийг "HEAD" гэдэг тусгай лавлагаа заадаг.

## Репо

Эцэст нь Git-ийн _repository_ (репо) гэж юу болохыг тодорхойлж болно: энэ бол
`objects` болон `references` гэсэн өгөгдөл л.

Дискэн дээр Git-ийн хадгалдаг зүйл нь ердөө объект ба лавлагаа. Git-ийн өгөгдлийн
загварт өөр далд юм байхгүй. Бүх `git` команд коммитуудын граф (DAG)-ыг өөрчилдөг:
шинэ объект нэмэх, эсвэл лавлагаа нэмэх/шинэчлэх замаар.

Команд ажиллуулах бүрдээ тэр команд графыг яг яаж өөрчилж байгааг бодож сураарай.
Эсрэгээр нь, граф дээр тодорхой өөрчлөлт хийхийг хүсвэл, жишээ нь "коммит хийгээгүй
өөрчлөлтүүдээ хаяад 'master' лавлагааг `5d83f9e` коммит руу заалгах" бол үүнийг
хийх команд бараг л байгаа (энэ тохиолдолд `git checkout master; git reset --hard 5d83f9e`).

# Staging area

Энэ бол өгөгдлийн загвараас тусдаа, гэхдээ коммит үүсгэх интерфейсийн нэг хэсэг
болох чухал ойлголт.

Снапшотыг ажлын хавтасны *одоогийн төлөвөөс* шууд үүсгэдэг гэж бодож магадгүй.
Зарим хувилбарын хяналтын хэрэгсэл ингэж ажилладаг, гэхдээ Git тэгдэггүй. Бид
цэвэрхэн снапшот авахыг хүсдэг. Одоогийн бүх өөрчлөлтийг шууд снапшот
болгох нь үргэлж тохиромжтой байдаггүй. Жишээ нь хоёр өөр боломж хөгжүүлчихээд
тэднийг хоёр тусдаа коммит болгомоор байна гэж бодъё. Эсвэл алдаа хайх явцдаа кодын
олон газар print тавьчихаад, тэдгээрийг оруулалгүй зөвхөн алдааны засвараа коммит
хийх хэрэгтэй байж болно.

Git дараагийн снапшотдоо аль өөрчлөлтүүдийг оруулахаа **staging area** (бэлтгэлийн
талбар) гэдэг механизмаар зааж өгөх боломж олгодог.

# Git-ийн командын мөрийн интерфейс

Мэдээллийг давхардуулахгүйн тулд лекцийн тэмдэглэлд командуудыг нэг бүрчлэн
тайлбарлахгүй. Дэлгэрэнгүйг [Pro Git](https://git-scm.com/book/en/v2) номоос
эсвэл лекцийн бичлэгээс үзээрэй.

## Үндсэн командууд

- `git help <command>`: Git-ийн командын тусламжийг харна
- `git init`: шинэ Git репо үүсгэнэ, өгөгдөл нь `.git` хавтаст хадгалагдана
- `git status`: одоогийн байдлыг харуулна
- `git add <filename>`: файлуудыг staging area-д нэмнэ
- `git commit`: шинэ коммит үүсгэнэ
    - [Сайн коммит мессеж](https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html)
      бичиж байгаарай!
    - Сайн коммит мессеж бичих [бүр олон шалтгаан](https://chris.beams.io/posts/git-commit/)!
- `git log`: түүхийг дараалсан жагсаалтаар харуулна
- `git log --all --graph --decorate`: түүхийг граф (DAG) хэлбэрээр харуулна
- `git diff <filename>`: staging area-тай харьцуулахад хийсэн өөрчлөлтүүдийг харуулна
- `git diff <revision> <filename>`: файлын хоёр снапшот хоорондын ялгааг харуулна
- `git checkout <revision>`: HEAD-ийг шинэчилнэ (салаа руу шилжиж байгаа бол
  одоогийн салааг ч солино)

## Салаа (branch) ба нэгтгэх (merge)

- `git branch`: салаануудыг харуулна
- `git branch <name>`: шинэ салаа үүсгэнэ
- `git switch <name>`: өөр салаа руу шилжинэ
- `git checkout -b <name>`: шинэ салаа үүсгээд шууд шилжинэ
    - `git branch <name>; git switch <name>`-тэй адил
- `git merge <revision>`: заасан салааг одоогийн салаа руу нэгтгэнэ
- `git mergetool`: нэгтгэлийн зөрчлийг (merge conflict) шийдэхэд туслах хэрэгслийг ажиллуулна
- `git rebase`: коммитуудын цувааг шинэ суурь коммит дээр шилжүүлнэ

## Алсын репо (remote)

- `git remote`: холбогдсон алсын репонуудыг жагсаана
- `git remote add <name> <url>`: алсын репо нэмнэ
- `git push <remote> <local branch>:<remote branch>`: объектуудыг алсын репо руу
  илгээж, алсын лавлагааг шинэчилнэ
- `git branch --set-upstream-to=<remote>/<remote branch>`: өөрийн болон алсын
  салааны холбоог тохируулна
- `git fetch`: алсын репогоос объект/лавлагаануудийг татна
- `git pull`: `git fetch; git merge`-тэй адил
- `git clone`: алсын репог бүтнээр нь дискэн дээрээ хуулна

## Буцаах

- `git commit --amend`: коммитын агуулга эсвэл мессежийг засна
- `git reset <file>`: файлыг staging area-аас гаргана
- `git restore`: өөрчлөлтүүдийг хаяж хуучин төлөвт нь оруулна

# Ахисан түвшний Git

- `git config`: Git [маш нарийн тохируулагддаг](https://git-scm.com/docs/git-config)
- `git clone --depth=1`: түүхийг бүтнээр нь биш, зөвхөн сүүлийн хэсгийг нь хуулна
  (shallow clone)
- `git add -p`: өөрчлөлтүүдээс хэсэг хэсгээр нь сонгож staging area-д нэмнэ
- `git rebase -i`: коммитуудыг интерактив байдлаар нэгтгэх, устгах, засах
- `git blame`: мөр бүрийг хамгийн сүүлд хэн засварласныг харуулна
- `git stash`: ажлын хавтасны өөрчлөлтүүдийг түр хадгалаад цэвэрлэнэ
- `git bisect`: түүхээс хоёртын хайлтаар алдааг олно (жишээ нь хэзээ эвдэрснийг)
- `git revert`: өмнөх коммитын өөрчлөлтийг эсрэгээр нь хийсэн шинэ коммит үүсгэнэ
- `git worktree`: олон салааг өөр өөр хавтаст зэрэг нээж ажиллана
- `.gitignore`: Git-ээр хянахгүй [файлуудыг заана](https://git-scm.com/docs/gitignore)

# Бусад сэдэв

- **GUI програмууд**: Git-д зориулсан олон [GUI
  програм](https://git-scm.com/downloads/guis) бий. Бид тэдгээрийг хэрэглэдэггүй,
  командын мөрийг илүүд үздэг.
- **Шеллтэй холбох**: Шеллийнхээ промпт дээр Git-ийн төлөвийг (одоогийн салаа
  гэх мэт) харуулах нь их эвтэйхэн
  ([zsh](https://github.com/olivierverdier/zsh-git-prompt),
  [bash](https://github.com/magicmonty/bash-git-prompt)). Ихэвчлэн
  [Oh My Zsh](https://github.com/ohmyzsh/ohmyzsh) зэрэг фреймворкт багтсан байдаг.
- **Засварлагчтай холбох**: Үүнтэй адил олон засварлагч Git-тэй холбогдох
  боломжтой. Vim-ийн хувьд стандарт хэрэгсэл нь [fugitive.vim](https://github.com/tpope/vim-fugitive).
- **Ажлын урсгал (ажлын урсгал)**: Бид өгөгдлийн загвар болон зарим үндсэн командыг
  заасан ч том төсөл дээр ажиллахдаа ямар дүрэм баримтлах талаар яриагүй
  ([олон](https://nvie.com/posts/a-successful-git-branching-model/)
  [өөр](https://www.endoflineblog.com/gitflow-considered-harmful)
  [арга](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow)
  бий).
- **GitHub**: Git бол GitHub биш. GitHub бусдын төсөлд хувь нэмэр оруулах өөрийн
  гэсэн аргатай, тухайлбал [pull request](https://help.github.com/en/github/collaborating-with-issues-and-pull-requests/about-pull-requests).
- **Бусад Git үйлчилгээ**: Ганц GitHub биш: [GitLab](https://about.gitlab.com/),
  [BitBucket](https://bitbucket.org/) гэх мэт олон репо байршуулах үйлчилгээ бий.

# Дасгал ажил

1. Git-тэй урьд нь ажиллаж байгаагүй бол [Pro Git](https://git-scm.com/book/en/v2)-ийн
   эхний хэдэн бүлгийг уншаарай, эсвэл [Learn Git Branching](https://learngitbranching.js.org/)-ийг
   тоглоод үзээрэй. Явцдаа Git-ийн командууд өгөгдлийн загвартай яаж холбогдож байгааг
   бодож байгаарай.
1. [Энэ хичээлийн вэбсайтын репо](https://github.com/missing-semester/missing-semester)-г
   clone хийгээрэй.
    1. Түүхийг нь граф хэлбэрээр харж судлаарай.
    1. `README.md`-г хамгийн сүүлд хэн засварласан бэ? (Сэжүүр: `git log`-ийг
       аргументтай нь хэрэглээрэй).
    1. `_config.yml`-ийн `collections:` мөрийг хамгийн сүүлд өөрчилсөн коммитын
       мессеж юу байсан бэ? (Сэжүүр: `git blame`, `git show` хэрэглээрэй).
1. Git сурч байхад гардаг түгээмэл алдаа бол Git-ээр удирдах ёсгүй том файл эсвэл
   нууц мэдээллийг коммит хийчихэх. Репод файл нэмээд, хэдэн коммит хийсний дараа
   тэр файлыг түүхээс (зөвхөн сүүлийн коммитоос биш) бүрмөсөн устгаж үзээрэй.
   [Үүнийг](https://help.github.com/articles/removing-sensitive-data-from-a-repository/)
   үзэж болно.
1. GitHub-аас нэг репо clone хийгээд, байгаа файлуудаас нь нэгийг засаарай.
   `git stash` хийхэд юу болж байна вэ? `git log --all --oneline` ажиллуулахад
   юу харагдаж байна? `git stash pop`-оор `git stash`-аар хадгалсан өөрчлөлтөө
   буцааж аваарай. Энэ ямар үед хэрэг болох вэ?
1. Олон командын мөрийн хэрэгслийн адил Git-д `~/.gitconfig` гэдэг тохиргооны файл
   (dotfile) бий. `~/.gitconfig` дотор alias үүсгээд `git graph` гэж бичихэд
   `git log --all --graph --decorate --oneline`-ийн гаралт гардаг болгоорой. Үүнийг
   `~/.gitconfig` файлыг [шууд засаж](https://git-scm.com/docs/git-config#Documentation/git-config.txt-alias),
   эсвэл `git config` командаар хийж болно. Git-ийн alias-ын талаар
   [эндээс](https://git-scm.com/book/en/v2/Git-Basics-Git-Aliases) уншаарай.
1. `git config --global core.excludesfile ~/.gitignore_global` ажиллуулсны дараа
   `~/.gitignore_global` дотор бүх репод хамаарах ignore хэв загваруудыг зааж
   болно. Энэ команд зөвхөн файлын байршлыг заадаг тул файлаа өөрөө үүсгэх
   хэрэгтэй. Глобал gitignore-доо үйлдлийн систем эсвэл засварлагчийн түр файлуудыг
   (жишээ нь `.DS_Store`) нэмээрэй.
1. [Энэ хичээлийн вэбсайтын репо](https://github.com/missing-semester/missing-semester)-г
   fork хийгээд үсгийн алдаа эсвэл өөр сайжруулах зүйл олж, GitHub дээр pull request
   илгээгээрэй ([үүнийг](https://github.com/firstcontributions/first-contributions)
   үзэж болно). Зөвхөн үнэхээр хэрэгтэй засвар илгээгээрэй (спам битгий хийгээрэй!).
   Засах юм олдохгүй бол энэ дасгалыг алгасаж болно.
1. Хамтын ажлын нөхцөлийг дуурайлгаж нэгтгэлийн зөрчил шийдэх дасгал хийгээрэй:
    1. `git init`-ээр шинэ репо үүсгээд, хэдэн мөртэй `recipe.txt` файл үүсгээрэй.
    2. Коммит хийгээд хоёр салаа үүсгээрэй: `git branch salty`, `git branch sweet`.
    3. `salty` салаа дээр нэг мөрийг өөрчлөөд (жишээ нь "1 cup sugar"-ыг
       "1 cup salt" болгоод) коммит хийгээрэй.
    4. `sweet` салаа дээр мөн тэр мөрийг өөрөөр өөрчлөөд (жишээ нь "1 cup sugar"-ыг
       "2 cups sugar" болгоод) коммит хийгээрэй.
    5. Одоо `master` руу шилжээд `git merge salty`, дараа нь `git merge sweet`
       хийгээд үзээрэй. Юу болж байна? `recipe.txt`-ийн агуулгыг хараарай ---
       `<<<<<<<`, `=======`, `>>>>>>>` тэмдэглэгээнүүд юуг илэрхийлж байна вэ?
    6. Файлаа засаж хүссэн агуулгаа үлдээгээд, зөрчлийн тэмдэглэгээнүүдийг устгаж,
       `git add`, `git commit` (эсвэл `git merge --continue`)-ээр нэгтгэлээ
       дуусгаарай. Эсвэл `git mergetool`-ийг ажиллуулж зөрчлийг график эсвэл
       терминал дээрх хэрэгслээр шийдэж үзээрэй.
    7. `git log --graph --oneline`-ээр саяын үүсгэсэн нэгтгэлийн түүхийг хараарай.
